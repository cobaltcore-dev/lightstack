# Feature Specification: Teardown via Helm Pre-Delete Hooks (Clean, No State Leakage)

**Feature Branch**: `010-helm-teardown` (work branch: `feature/53-teardown-via-helm-pre-delete-hooks-clean-no-state-leakage`)
**Created**: 2026-06-15
**Status**: Draft — 9 clarifications (3 rounds, 2026-06-15). **Scope revised 2026-06-24 (post-#503): DB reset DROPPED (database is operator-owned); storage + network purge widened to the full host inventory — see the scope note in Clarifications.** Engine + chart implemented + unit/render-tested; real-mode host e2e is cluster-gated.
**Tracking Issue**: [#53 — Teardown via Helm pre-delete hooks (clean, no state leakage)](https://github.com/cobaltcore-dev/o3k/issues/53)
**Input**: User description (issue #53): "A pre-delete hook Job that runs o3k's cleanup before the release is removed — purging network namespaces/routes, libvirt domains, and orphaned storage — so the next run starts from a pristine baseline."

> **Sequencing**: This feature is the deferred **destructive** half of SPEC-008 (`docs/specs/008-helm-charts/`). SPEC-008 shipped the chart, plain `helm uninstall` (workload removal, SC-006), and the default `dataRetentionPolicy: retain`; it explicitly **deferred the active purge** — the blocking pre-delete cleanup hook behind `dataRetentionPolicy: delete` — to this issue (#53). See SPEC-008 FR-014, T029, and the `dataRetentionPolicy` value, all annotated accordingly. This spec extends the existing chart; it does not introduce a new chart.

> **Reality check (from the codebase, 2026-06-15)**: The product has **no cleanup/teardown/purge entrypoint today** — the `o3k` binary parses only `--config` and `--migrations` (`cmd/o3k/main.go`). Per-resource delete paths exist and are reusable (`VMManager.DeleteVM`, `NetworkNamespaceManager.DeleteNamespace`, `RouterManager.DeleteRouterNamespace`, bridge/TAP deletes, Glance/Cinder per-item deletes, and `o3k-migrate reset` which drops the schema), but **no bulk, release-scoped purge** is wired. The chart creates **no PVCs** (real-mode node-local data lives on a `hostPath`, default `/var/lib/o3k`) and **no RBAC** (no ServiceAccount/Role). This feature must therefore build a product cleanup operation, the blocking hook, and the RBAC the hook needs. Further verified 2026-06-15 (round-3 audit): local Glance images write to `/var/lib/o3k/images` (on the chart's hostPath mount) but local Cinder volumes write to `~/.o3k/volumes` (off-mount, ephemeral) — fixed by FR-020; the teardown does **not** reset the operator-owned database (FR-013, revised 2026-06-24 — `o3k-migrate reset` / `MigrateReset` no longer used); and WS-6 startup network reconciliation is **not** implemented (issue #52).

## Clarifications

### Session 2026-06-15 (resolved — carried from SPEC-008)

- Q: What is the entry point for this behavior? → A: The existing `dataRetentionPolicy` value (`retain` | `delete`). `retain` is the default and preserves SPEC-008's current behavior (remove only the release's Kubernetes objects; leave persisted/runtime state untouched). `delete` triggers the purge specified here. The destructive path is **opt-in**.
- Q: Is the cleanup a separate artifact? → A: No. Per the constitution (Library-First, CLI Interface), the cleanup MUST be an invokable operation of the existing single O3K binary, callable by the hook — not a second image or sidecar tool.
- Q: How is "pristine" judged? → A: An install issued immediately after a `delete` teardown comes up healthy with no naming collisions and no residual-state errors (issue #53 acceptance criterion 3), measured the same way as a first install (SPEC-008 SC-001/SC-006).

### Session 2026-06-15 (clarification decisions — all RESOLVED via `/clarify`)

These five questions materially changed scope, blast radius, and which acceptance criteria the chart can satisfy alone. **All five were resolved on 2026-06-15** (decisions inline below and folded into the Functional Requirements; concise Q→A log in the resolutions session that follows).

> **SCOPE CHANGE — 2026-06-24 (post-#503).** Two decisions were revised once #503 (single-node real mode) landed and the cleanup was implemented against it:
> 1. **DB reset DROPPED.** C1 is reversed from option (b) (reset the schema) to **option (c): the database is operator-owned and is NOT touched** — teardown reads it only to enumerate. A pristine *resource* view on redeploy is now the operator's responsibility (supply a clean DB). This supersedes the DB-reset wording in C1, FR-009, FR-013, and FR-019 below.
> 2. **Purge scope widened to the full host inventory.** Storage purge now removes **all** node-local trees under `/var/lib/o3k` (`instances/` VM disks, `cloud-init/` ISOs, `images/`, `volumes/`, `dhcp/`), not just images+volumes (FR-005); network purge now removes **all** host state — bridges, SNAT / floating-IP / security-group / metadata iptables, dnsmasq — via `neutron.PurgeRealModeNetworkState`, not just the namespaces (FR-004). The global `net.ipv4.ip_forward` sysctl is deliberately left as-is (host-wide).

- **C1 — Database records on `delete`.** The external database is operator-owned (SPEC-008 FR-006: the chart never deploys a DB). But the DB holds every resource record; if it is reused across a teardown and a redeploy, stale instances/networks/volumes survive and startup network reconciliation (SPEC-008 FR-012g / WS-6) would rebuild networks for VMs that no longer exist — a "residual-state error." So a chart-only "pristine redeploy" is impossible unless the purge also clears the DB. Options: **(a)** purge only the release's rows from the shared schema; **(b)** drop/recreate the o3k schema (reuse `o3k-migrate reset`); **(c)** leave the DB untouched and document that pristine redeploy requires a fresh database/schema. **RESOLVED (/clarify 2026-06-15) → Option (b):** on `delete`, drop & recreate the O3K schema in the release's configured database (reuse `o3k-migrate reset`), with a loud "this destroys all O3K data in the configured database" warning. Release-scoped because each release owns its database (sharing one schema would break SPEC-008 isolation). *(Mechanism refined by C8/D2: reset via the `database.MigrateReset()` library function directly, not the interactive `o3k-migrate reset` CLI.)* **SUPERSEDED 2026-06-24 → Option (c):** the database is left untouched (operator-owned) — teardown reads it to enumerate but never resets it; a pristine redeploy requires the operator to supply a clean database. See the 2026-06-24 scope note above + FR-013/FR-009.
- **C2 — Multi-node host-state reach.** Network namespaces, libvirt domains, and `hostPath` data are **per node** and reachable only from a privileged pod on that node with the host mounts. A single pre-delete Job lands on one node and cannot purge the others. Options: **(a)** scope full host purge to single-node now and **defer** multi-node host purge to issue #52 (consistent with SPEC-008's round-8 gating of all multi-node/real e2e); **(b)** fan out per-node cleanup (e.g. a short-lived per-node mechanism the blocking Job waits on); **(c)** clean each node's own host state from that node's instance as it terminates, with the Job handling cluster/DB/backend state. **RESOLVED (/clarify 2026-06-15) → Option (a):** single-node host purge in scope & validated now; multi-node host purge **deferred to issue #52** (requires functioning cross-node real mode; the per-node mechanism — fan-out Job vs. per-instance terminating cleanup — is chosen at plan time when #52 lands). A pointer to the needed work is added to issue #52.
- **C3 — PVCs vs. `hostPath`.** Issue #53 names "PVCs, which Helm does not delete by default," but the chart creates **no PVCs today** (node-local data is a raw `hostPath`). Options: **(a)** delete release-owned PVCs **if any exist** and purge the `hostPath` data that is the current reality; **(b)** additionally change SPEC-008 to back node-local storage with PVCs so "delete PVCs" is always meaningful (storage-model change, larger scope). **RESOLVED (/clarify 2026-06-15) → Option (a):** the hook deletes any release-owned PVCs **if present** and purges the configured `hostStoragePath`; converting `hostPath`→PVC is **out of scope**. Rationale: O3K's node-local real-mode data is intrinsically node-bound (libvirt disks co-located with host `qemu`), a node-correct PVC would just be `hostPath` with extra bookkeeping, and real-mode teardown already needs a privileged host-mounted step (netns/libvirt) that can purge the directory for free. Multi-node real uses networked RBD/S3 (operator-owned, see C4), not local storage — mirroring OpenStack.
- **C4 — Networked backends (Ceph RBD / S3).** SPEC-008 treats RBD/S3 as operator-owned and shared. Purging the release's images/volumes from a shared backend is high blast-radius. Options: **(a)** do not auto-delete networked-backend data; document it as operator-owned and out of teardown scope; **(b)** delete only artifacts the product can unambiguously attribute to the release, gated behind `delete` with a warning. **RESOLVED (/clarify 2026-06-15) → Option (a):** teardown does **not** auto-delete networked-backend (RBD/S3) data; it is operator-owned and out of teardown scope, documented as such. Only node-local `hostPath` storage is purged. Leftover backend bytes don't break a pristine redeploy, since the DB reset (C1) leaves the new install referencing none of them.
- **C5 — Blocking semantics and failure UX.** A blocking hook that hangs blocks uninstall indefinitely. Options for bound/behavior: hook timeout, what counts as "success" (best-effort vs. all-or-nothing), and whether a failed purge halts uninstall (criterion 1) or warns-and-proceeds. **RESOLVED (/clarify 2026-06-15) → Option (a):** fail-closed with a bounded timeout and an escape hatch. The hook is best-effort per artifact but FAILS — halting uninstall with a clear, actionable error — if any required class of state could not be purged (honoring criterion 1). A bounded, configurable timeout prevents an indefinite hang; a documented operator override (skip flag / revert to `retain`) forces release removal when cleanup is genuinely impossible (e.g., the hosting node is gone).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - One-command clean teardown, nothing left behind (Priority: P1)

A platform operator is done with an O3K release on a single node (it ran real VMs, tenant networks, and local volumes/images). They want it gone — not just the Kubernetes objects, but the libvirt domains, the network namespaces and routes, and the node-local storage it created — in one command, with the guarantee that the uninstall does not "finish" until the cleanup has actually succeeded. They set `dataRetentionPolicy: delete` and run `helm uninstall`.

**Why this priority**: This is the feature. It is issue #53's acceptance criteria 1 and 2. Without it, `helm uninstall` leaves host-level debris (domains, namespaces, files) that the platform never reclaims and that collides with the next install. It is the minimum viable, independently demonstrable deliverable.

**Independent Test**: On a single node, install the chart in real mode (or stub with simulated state), create resources (server, network, volume, image), then `helm uninstall` with `dataRetentionPolicy: delete`. Verify the uninstall blocks until the cleanup Job succeeds, then verify zero release-owned artifacts remain: no release workloads/services, no release PVCs, no libvirt domains, no `light-ns-*`/`qrouter-*` namespaces or their routes/bridges, and an empty (or removed) node-local storage path for the release.

**Acceptance Scenarios**:

1. **Given** a running single-node release with real compute/network/storage state and `dataRetentionPolicy: delete`, **When** the operator runs `helm uninstall`, **Then** a pre-delete hook runs the product's cleanup, and the release's resources are **not** removed until that cleanup reports success (the hook is blocking).
2. **Given** the same teardown completes, **When** the operator inspects the node and cluster, **Then** no libvirt domain, network namespace, route, bridge, or node-local storage created by the release remains, and any release-owned PVC has been deleted (PVCs are not removed by `helm uninstall` by default — they are handled explicitly).
3. **Given** the cleanup cannot complete (e.g., a required class of state cannot be purged), **When** the hook fails, **Then** `helm uninstall` halts with a clear error rather than silently leaving state behind, and the operator is told what could not be cleaned.

---

### User Story 2 - Immediate clean redeploy from a pristine baseline (Priority: P2)

Right after tearing a release down, the operator (or a CI pipeline, or a GitOps reconcile) installs it again — same release name, same node, same configured database. It must come up healthy as if installed on fresh infrastructure: no name already in use, no leftover namespace, no stale records resurrecting dead networks.

**Why this priority**: This is issue #53 acceptance criterion 3 and the whole point of "pristine baseline." A teardown that purges state but still fails the next install has not delivered the value. It depends on US1 having actually removed the state.

**Independent Test**: Execute a `delete` teardown (US1), then immediately reinstall the chart with the same release name and node. Verify the install succeeds, the built-in identity verification (SPEC-008 FR-015) passes within the normal install time budget, and no naming-collision or residual-state error occurs (e.g., no "namespace already exists," no servers/networks from the previous release listed by the API).

**Acceptance Scenarios**:

1. **Given** a release was just torn down with `dataRetentionPolicy: delete`, **When** the operator installs the chart again immediately with the same release name on the same node, **Then** installation succeeds and the identity endpoint reports healthy with no manual intervention.
2. **Given** the reinstalled release, **When** the operator lists resources via the standard OpenStack CLI, **Then** no instances, networks, volumes, or images from the prior release are present (the baseline is pristine).
3. **Given** the reinstalled release on a node where the previous release ran real VMs, **When** it starts, **Then** no name collision occurs against leftover libvirt domains or network namespaces, because none survived the teardown.

---

### User Story 3 - Explicit, safe retain-vs-delete choice (Priority: P3)

An operator must never destroy persisted data by accident. The default stays `retain` (today's behavior: remove the release's Kubernetes workloads, keep all data and runtime state). Destruction happens only when the operator consciously selects `delete`, and that choice is documented, loud, and irreversible-by-design. Re-running a teardown (e.g., a retried uninstall, or a release whose state was already partly removed) is safe and does not wedge.

**Why this priority**: Safety and operability make the feature production-credible, but they only matter once the purge (US1) and clean redeploy (US2) work. This story also carries the operator-owned-database/backends nuance and the idempotency guarantee.

**Independent Test**: (a) Uninstall with the default `retain` and confirm behavior is identical to SPEC-008 today — workloads/services gone, persisted/runtime data untouched. (b) Uninstall with `delete` and confirm data is purged. (c) Re-run the `delete` teardown against an already-clean (or partially-clean) release and confirm it succeeds without error. (d) Confirm the values reference documents the destructive semantics and what the chart does **not** own (e.g., the external DB and networked backends, per the resolved clarifications).

**Acceptance Scenarios**:

1. **Given** the default `dataRetentionPolicy: retain`, **When** the operator runs `helm uninstall`, **Then** all release workloads and services are removed and no persisted or runtime state is touched — identical to SPEC-008's current behavior (no regression to SC-006).
2. **Given** `dataRetentionPolicy: delete`, **When** the operator uninstalls, **Then** the purge runs only because it was explicitly selected; no code path destroys persisted data under the default.
3. **Given** a release whose host/cluster state is already partly gone (a retried or interrupted teardown), **When** the cleanup runs again, **Then** missing or already-deleted artifacts are treated as success (idempotent), not as errors, and the hook completes.
4. **Given** an operator reviewing the chart's configuration reference, **When** they read the teardown values, **Then** the destructive semantics, irreversibility, and what remains operator-owned (per C1/C4) are documented with purpose, default, and applicable mode(s).

---

### Edge Cases

- **Multi-node host state on N nodes**: host artifacts (domains, namespaces, `hostPath`) exist on every DaemonSet node, but a single pre-delete Job runs on one node. How is each node's host state purged? (See C2; recommended: single-node in scope now, multi-node host purge gated on issue #52.)
- **Shared external database reused across teardown/redeploy**: stale records would resurrect dead networks via startup reconciliation. Is the DB purged, and at what scope? (See C1.)
- **Shared networked backend (RBD/S3) holding other releases' data**: deleting by release is high blast-radius. (See C4; recommended: not auto-deleted, documented as operator-owned.)
- **PVCs that do not exist yet**: the chart uses `hostPath`, not PVCs, today. The hook must delete PVCs *if present* and purge the `hostPath` data regardless. (See C3.)
- **Cleanup partially fails** (e.g., a domain refuses to undefine, a namespace is busy): does uninstall halt (criterion 1) or warn-and-proceed? What is the bound on a blocking hook so it cannot hang forever? (See C5.)
- **VMs are host processes that survive pod restarts**: a teardown deliberately destroys them — this is the one lifecycle event that MUST terminate surviving VMs (the opposite of upgrade survival in SPEC-008 FR-012c). Confirm the purge reaches the host libvirtd, not just pod children.
- **Hook needs Kubernetes permissions** the chart has never granted (no RBAC today): deleting PVCs requires a release-scoped ServiceAccount + Role/RoleBinding the hook can use; absent it, PVC deletion fails.
- **`retain` + leftover state**: with the default, the operator keeps data deliberately; the chart must not purge it, and must document how to clean node-local data manually (today's documented behavior).
- **Teardown invoked when there was never any real state** (pure stub release): the cleanup must be a clean no-op and succeed.
- **Uninstall race with the workload**: Helm runs the pre-delete hook *while the release's pods are still live* (it deletes the workload only after the hook completes). To stop a live instance from erroring through the DB schema reset (and, once WS-6 lands per #52, from reconciling purged state back — WS-6 is not implemented today), the hook MUST **quiesce the workload first** (single-node: scale the Deployment to 0), then enumerate from the DB → purge host/storage → reset the DB last. VMs survive the control-plane stop (host processes); the Job still purges their domains. (See C6.)
- **Database unreachable at teardown**: the cleanup ignores the DB — no enumeration, no reset — and does not fail on that account; host state is purged best-effort via host-level enumeration (netns prefix scan, libvirt domain list). (See C9.)
- **Cinder local volumes are written off the hostPath mount today** (`~/.o3k/volumes`, ephemeral) while Glance uses `/var/lib/o3k/images`; the purge would miss them and they don't persist anyway. FR-020 fixes the path. (See C7.)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Teardown MUST be implemented as a Helm **pre-delete hook** that runs the product's cleanup and is **blocking** — the release's Kubernetes resources MUST NOT be removed until the cleanup reports success. If the cleanup fails, `helm uninstall` MUST halt with a clear, actionable error (issue #53 criterion 1).
- **FR-002**: The destructive teardown MUST be gated behind the existing `dataRetentionPolicy` value. `retain` (the default) MUST preserve SPEC-008's current behavior exactly (remove only the release's Kubernetes workloads/services; leave all persisted and runtime state untouched). The purge MUST run only when `delete` is explicitly selected; no code path may destroy persisted data under the default.
- **FR-003**: On `delete`, the cleanup MUST purge **compute** state: every libvirt domain the release created MUST be destroyed and undefined on the hosting node, including VMs that are host `libvirtd` processes surviving pod lifecycle (the one event that intentionally terminates them, contrary to upgrade survival).
- **FR-004**: On `delete`, the cleanup MUST purge **network** state created by the release: tenant and router network namespaces (`light-ns-*`, `qrouter-*`), bridges, veth/TAP devices, routes, `iptables`/security-group rules, and overlay (VXLAN) interfaces — so no O3K network artifact survives on the cleaned node(s).
- **FR-005**: On `delete`, the cleanup MUST purge **storage** state: **all** node-local trees under the configured host storage path (`/var/lib/o3k`) — VM disk overlays (`instances/`), config-drive ISOs (`cloud-init/`), Glance images (`images/`), Cinder volumes (`volumes/`), and dnsmasq state (`dhcp/`) — and any **PersistentVolumeClaims owned by the release** (explicitly, because `helm uninstall` does not delete PVCs by default — issue #53 criterion 2). Where the chart provisions no PVCs (current reality — `hostPath` only), the `hostPath` data MUST still be purged; release-owned PVCs MUST be deleted **if present**. The chart MUST NOT convert node-local storage from `hostPath` to PVCs. All node-local data MUST live under the configured host storage path so the purge reaches it (FR-020 fixed the Cinder path). *(Resolved via /clarify — C3; scope widened to all node-local trees 2026-06-24; path consistency per C7/FR-020.)*
- **FR-006**: On `delete`, the cleanup MUST remove **orphaned** storage — artifacts whose database record is already gone but whose bytes remain (partial-delete leftovers) — to the extent the product can attribute them to the release.
- **FR-007**: The purge MUST be **release-scoped**: it MUST affect only the uninstalled release's resources and MUST NOT touch co-resident releases or unrelated host state (the SPEC-008 FR-016 isolation guarantee MUST hold through teardown).
- **FR-008**: The cleanup MUST be **idempotent and fail-safe**: a missing or already-deleted artifact MUST be treated as success, not an error; pre-existing partial state MUST NOT wedge the hook; re-running teardown MUST succeed.
- **FR-009**: After a `delete` teardown, an install issued **immediately afterward** (same release name and node) MUST succeed and reach healthy with no naming collisions and no *host* residual-state errors (issue #53 criterion 3). Because the database is operator-owned and is NOT reset (FR-013), a *resource*-pristine redeploy (no stale instances/networks) requires the operator to supply a clean database; teardown guarantees only that no o3k host state or Kubernetes object collides. *(Scope revised 2026-06-24 — see the scope note.)*
- **FR-010**: The product MUST expose the cleanup as an explicit, invokable operation of the **existing single O3K binary** (a command/entrypoint), so the hook can call it without a separate artifact or sidecar image (constitution: Library-First, CLI Interface). *(This operation does not exist today and MUST be built; it SHOULD reuse the existing per-resource delete paths and the database as the source of truth for what to purge.)*
- **FR-011**: The chart MUST grant the pre-delete hook exactly the Kubernetes permissions it needs and no more — a **release-scoped ServiceAccount, Role, and RoleBinding** sufficient to quiesce the release's workload (scale the Deployment to 0, per C6/FR-019) and to delete release-owned PVCs (and any other release-owned objects it must remove). *(No RBAC exists in the chart today; it MUST be added for the hook.)*
- **FR-012**: The teardown MUST be **observable**: it MUST emit the product's structured JSON logs recording what it purged, what it skipped (already-absent), and what it failed to purge, so an operator can audit a teardown (consistent with SPEC-008 FR-013a).
- **FR-013** *(revised 2026-06-24 — reverses the original C1 reset decision)*: On `delete`, the teardown MUST NOT reset, drop, or modify the configured database — it is **operator-owned**. The cleanup reads the DB read-only to enumerate what host state to purge, but never writes to it. The database lifecycle belongs to its operator (e.g. a Kubernetes DB operator); a pristine *resource* view on redeploy is the operator's responsibility (supply a clean database). Consequently the `o3k cleanup` command takes no `--migrations` flag and does not call `MigrateReset`. *(Original C1/C8 decision — reset the schema via `database.MigrateReset()` — is superseded; see the 2026-06-24 scope note.)*
- **FR-014**: Single-node host-state purge MUST be in scope and validated in this feature. **Multi-node** (DaemonSet) host-state purge — removing netns/routes, libvirt domains, and `hostPath` data on every labeled node — is **DEFERRED to issue #52**, because it requires functioning cross-node real mode (itself gated on #52); the eventual per-node mechanism (fan-out Job vs. per-instance terminating cleanup) is chosen when #52 is implemented. A pointer to the required multi-node teardown work MUST be recorded in issue #52. *(Resolved via /clarify — C2.)*
- **FR-015**: Teardown MUST NOT auto-delete data on networked storage backends (Ceph RBD, S3) — they are operator-owned and shared (mirroring OpenStack's shared Ceph/Swift). The cleanup MUST purge only node-local `hostPath` storage and MUST document that networked-backend volumes/images remain operator-owned and are not removed by teardown. *(Resolved via /clarify — C4.)*
- **FR-016**: The blocking hook MUST be **fail-closed and bounded**: best-effort per artifact, but it MUST fail — halting `helm uninstall` with a clear, actionable error — when any required class of state could not be purged (honoring FR-001 / criterion 1). It MUST enforce a bounded, configurable timeout so it cannot hang uninstall indefinitely, and MUST provide a documented operator override (e.g., a skip flag, or reverting to `retain`) to force release removal when cleanup is genuinely impossible (such as the hosting node being gone). *(Resolved via /clarify — C5.)*
- **FR-017**: With the default `retain`, the teardown MUST NOT regress SPEC-008's SC-006 — `helm uninstall` MUST still remove all release workloads and service endpoints with zero orphaned workloads.
- **FR-018**: Every new or changed configuration value and the destructive semantics MUST be documented with purpose, default, and applicable mode(s) (SPEC-008 FR-017/SC-007), including a loud warning that `delete` is irreversible and a statement of what remains operator-owned (DB, networked backends per C1/C4). The following existing docs MUST be reconciled when this feature ships: **`charts/o3k/README.md`** (the "clean node-local data manually when `delete`" line is superseded by the auto-purge — a direct contradiction once #53 ships; plus the terse `dataRetentionPolicy` values-table entry), **`charts/o3k/values.yaml`** (the `dataRetentionPolicy` comment must document the quiesce, DB reset, blocking semantics, and operator-owned boundaries), and the **SPEC-008** descriptions of the deferred purge (`spec.md` FR-014, `data-model.md`, `tasks.md` T027/T029, `quickstart.md`), which omit the DB reset and quiesce steps.
- **FR-019**: Because Helm runs the pre-delete hook while the release's workload is still live, the cleanup MUST **quiesce the workload before purging** — stop the release's instances (single-node: scale the Deployment to 0) so no instance serves requests, holds open database connections, or **re-creates purged state**. The re-creation hazard is now the primary reason: O3K's network reconciler (`internal/neutron/reconciler.go`, #503 WS-2) rebuilds host network state from the database on a poll, and because teardown does NOT reset the operator-owned DB (FR-013), a still-running reconciler would immediately undo the purge — so quiescing is essential. It MUST then enumerate the release's state from the database **read-only** and purge host + storage state. **If the database is unreachable, the cleanup MUST ignore it** — and MUST NOT fail the teardown on that account; host-state purge then proceeds best-effort via host-level enumeration (netns prefix scan of `light-ns-*`/`qrouter-*`). *(Resolved via /clarify — C6; scope revised 2026-06-24 — no DB reset; DB-unreachable per C9/D3.)*
- **FR-020**: Node-local storage paths MUST be consistent and located under the chart-mounted host storage path. This feature MUST fix the current Cinder local-volume path — `pkg/storage/ceph.go` writes volumes to `~/.o3k/volumes`, which is **off the hostPath mount** (ephemeral pod storage) — to use `<hostStoragePath>/volumes`, mirroring Glance's `<hostStoragePath>/images` (and the path the reference Dockerfile already pre-creates). Without this, local Cinder volumes neither persist across pod restarts (a latent SPEC-008 FR-012a defect) nor are reachable by the storage purge (FR-005). The path SHOULD be configurable, with the `~/.o3k` location retained as a non-container fallback. *(Resolved via /clarify — C7/D1.)*

### Key Entities *(include if feature involves data)*

- **Teardown Operation**: The product's release-scoped purge action. Runs after the workload is quiesced (C6); enumerates the release's state from the database **before** the DB is reset, then removes host/storage state in dependency-safe order (instances/domains → ports/networks/namespaces → storage) and resets the database **last**, best-effort and idempotent. The thing the hook invokes (FR-010).
- **Data Retention Policy**: The `retain` | `delete` selector that gates destruction; the operator's explicit, documented choice (FR-002).
- **Pre-Delete Hook (blocking Job)**: The Helm lifecycle object that runs the Teardown Operation before resource removal, plus its release-scoped RBAC (ServiceAccount/Role/RoleBinding). Blocking and bounded (FR-001/FR-011/FR-016).
- **Release-Scoped State**: The full set of artifacts attributable to one release — Kubernetes objects, PVCs, host libvirt domains, network namespaces/routes/bridges, node-local storage, and (per C1/C4) database records and networked-backend data. The thing a teardown must fully account for.
- **Compute Domain / Network Namespace / Storage Artifact / PVC**: The concrete per-class artifacts the purge removes; named/locatable by the product's existing conventions (e.g. `light-ns-<project>`, `qrouter-<router>`, host storage path).
- **Pristine Baseline**: The post-teardown state in which an immediate redeploy of the same release on the same node and database succeeds with no collisions or residual-state errors (FR-009; issue #53 criterion 3).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After a `delete` teardown of a single-node release, **zero** release-owned artifacts remain — measured as an inventory of release workloads/services, release PVCs, libvirt domains, network namespaces/routes/bridges, and node-local storage entries all equal to zero.
- **SC-002**: An install issued **immediately** after a `delete` teardown (same release name, node, and database) reaches a healthy identity endpoint within the same time budget as a first install (SPEC-008 SC-001), with no naming-collision or residual-state error.
- **SC-003**: `helm uninstall` does **not** report completion while the cleanup is unfinished — release resources remain present until the hook reports success (blocking behavior verified by observing the uninstall block on the hook).
- **SC-004**: With the default `retain`, `helm uninstall` behaves **identically** to SPEC-008 today — all release workloads/services removed, persisted/runtime state untouched — i.e., SPEC-008 SC-006 is preserved with no regression.
- **SC-005**: Re-running a `delete` teardown against already-clean or partially-clean state **succeeds** (idempotency), verified by a second run exiting successfully with no errors.
- **SC-006**: 100% of destructive behavior is **opt-in and documented** — no automated path destroys persisted data without the operator explicitly selecting `delete`, and the values reference documents the destructive semantics and operator-owned boundaries.
- **SC-007** *(Deferred — gated on issue #52, mirroring SPEC-008 SC-003/004)*: In multi-node mode, a `delete` teardown purges host state on every node that ran an instance, validated end-to-end once the real-mode/multi-node post-conditions ship.

## Assumptions

- **Extends SPEC-008**: This feature modifies the existing `charts/o3k/` chart; the `dataRetentionPolicy` value is already present (added by SPEC-008) as the documented entry point. No new chart is introduced.
- **No cleanup command exists yet**: Confirmed from the codebase — the `o3k` binary has no teardown/cleanup/purge subcommand; only per-resource delete paths and `o3k-migrate reset` (DB schema only) exist. This feature builds the cleanup operation, reusing those paths and the database as the source of truth.
- **Node-local storage is `hostPath` today, not PVCs**: The chart provisions no PVCs; real-mode data lives under a `hostPath` (default `/var/lib/o3k`). The PVC-deletion requirement therefore applies to release-owned PVCs **if present**; converting node-local storage to PVCs is out of scope unless C3 decides otherwise.
- **No RBAC exists today**: The chart defines no ServiceAccount/Role; the hook's PVC deletion requires adding release-scoped RBAC.
- **External database and networked backends are operator-owned** (SPEC-008 FR-006 and backend-ownership stance). Their teardown treatment is the subject of clarifications C1 and C4; the chart MUST NOT silently destroy operator-owned data.
- **Host-state purge is inherently node-local**: VMs are host `libvirtd` processes and namespaces/`hostPath` live on the node, reachable only from a privileged pod on that node with the host mounts — so multi-node host purge cannot be done from a single Job without per-node reach (C2).
- **Multi-node/real-mode e2e is gated on issue #52** (SPEC-008 round-8). Teardown follows the same gating: single-node host purge is the validated MVP here; multi-node host purge validation is deferred to #52.
- **Teardown is the deliberate VM-killing event**: unlike upgrades (where VMs survive pod restarts per SPEC-008 FR-012c), a `delete` teardown intentionally destroys surviving VMs.
