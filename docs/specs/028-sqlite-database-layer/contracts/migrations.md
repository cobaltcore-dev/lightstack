# Contract: one migrations folder for both backends

Covers FR-024 – FR-031 and US5 (research R10 – R12, R20).

## File names

```text
migrations/
  NNN_<name>.up.sql / .down.sql                        plain: PostgreSQL 001–073 today; from 074 on, both backends
  073_baseline.sqlite.up.sql / .down.sql               SQLite starts here (generated, research R11)
  NNN_<name>.postgres.up.sql + NNN_<name>.sqlite.up.sql  dialects differ: a pair under one number (+ .down pairs)
  README.md                                            rules and conventions (not a migration)
```

## Rules of a backend's view

1. A `.postgres` or `.sqlite` file is used only by that backend.
2. A backend's own file for a version replaces the plain file with that number.
3. SQLite skips every version below its baseline (the number of `NNN_baseline.sqlite.up.sql`).

Down files follow the same rules. `ValidateMigrations` checks each view: every up has a down and the reverse, a backend's own up file has a down file of its own, exactly one SQLite baseline, no duplicate version after the rules. A backend's own down file beside a plain up file is allowed: it corrects how that backend rolls the plain file back. The plain down files of `010`, `019`, `028` and `037` dropped tables and columns an earlier migration owned; being below the baseline, they are PostgreSQL's alone and were corrected in place (2026-10-13; first as `.postgres.down.sql` overrides, T085).

## Behaviour per backend

| Action | PostgreSQL | SQLite |
|---|---|---|
| `up` on an empty database | 001 … newest | baseline, then every later version |
| `up` on a current database | no change | no change |
| `down` / `reset` | as today | down to the baseline, then the baseline's down (empty database) |
| `goto V` / `force V` with V below the baseline | as today | refused: `SQLite starts at its baseline 073; version V is below it` |
| locking | golang-migrate's advisory lock (unchanged) | exclusive `flock` on `<db>.migrate-lock` (0600) for the whole run, up to 15 s, then an error naming the lock file |
| connection | the URL, through golang-migrate's postgres driver | Lightstack's SQLite opener, a dedicated `*sql.DB` per run; create-if-missing for `up`/`goto`/`reset`, must-exist for `status`/`down`/`force` (a mistyped path is an error, not a new empty database) |

## Tools

| Command | After this feature |
|---|---|
| `lightstack` (startup) | migrates up through the backend's view |
| `lightstack-migrate status\|up\|down\|reset\|goto\|force` | same commands, backend from `database.url` / `LIGHTSTACK_DB_URL` |
| `make migrate` | `LIGHTSTACK_DB_URL="$(DB_URL)" go run ./cmd/lightstack-migrate up -migrations migrations` |
| `make install-tools` | no longer installs golang-migrate's `migrate` CLI, which cannot read the folder once a `.sqlite` file shares a version and would apply the SQLite baseline to PostgreSQL |

## Conventions for later changes (`migrations/README.md`)

- One plain file only for SQL both backends spell and treat alike — `TEXT` strings and `INTEGER`/`BIGINT` numbers: `ADD COLUMN` without `IF NOT EXISTS` of a nullable `TEXT`/`INTEGER` column or one with a constant default; `DROP COLUMN` of an unindexed column; `CREATE INDEX`.
- A pair whenever the backends differ — which is every `CREATE TABLE` (PostgreSQL ids are `UUID` and timestamps `TIMESTAMPTZ`, but on SQLite both are `TEXT`: a `TEXT` id cannot reference a `UUID` key and pgx will not scan `TEXT` into `time.Time`, and a `STRICT` table admits only `INT`/`INTEGER`/`REAL`/`TEXT`/`BLOB`/`ANY`), and any boolean, timestamp, id/uuid, JSON or list column. Also a column added with a non-constant default (SQLite refuses `ADD COLUMN … DEFAULT (now())`) or `NOT NULL` without a default, a type change, or a constraint change (the `.sqlite` file rebuilds the table). Only a table nothing references may be rebuilt: every file runs in a transaction with foreign keys on, and dropping a referenced table deletes the referencing rows through `ON DELETE CASCADE` (research R20). The first rebuild of a referenced table comes with a migrator change that lets one file run outside a transaction.
- Ids are generated by the application in new tables; timestamps the application writes are bound, not defaulted, when a column is added later.
- The parity test (FR-028) must stay green: every pair produces the same tables, columns, nullability, defaults, keys, CHECKs, seed rows and indexes.
