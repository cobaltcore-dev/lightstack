# Feature Specification: Helm Charts for Kubernetes Deployment (Single-Node and Multi-Node)

**Feature Branch**: `008-helm-charts`
**Created**: 2026-06-02
**Status**: Draft — **chart-shaping prerequisites (SPEC-007) complete; real/multi-node post-conditions sequenced after the chart**

> **Sequencing**: The chart-shaping prerequisites are **SPEC-007** (`docs/specs/007-helm-prereqs-bootstrap-catalog/`) — admin-password bootstrap wiring (FR-007a, all modes) and the configurable catalog scheme (FR-008b, TLS only); both are **implemented**, so chart authoring is unblocked. The remaining product changes — multi-node VM placement & request forwarding, metadata reachability, north-south networking, and startup network reconciliation — are **post-conditions** (`SPEC-007-POSTCONDITIONS.md`; workstreams WS-1/WS-4/WS-5/WS-6): internal product/runtime work that does **not** change the chart's manifests but that real-mode and multi-node deployments need in order to fully function. They are sequenced **after** the chart is authored. Net effect: single-node stub mode (and optional TLS) is fully functional now; the real-mode and multi-node paths are authorable now and become functional once the post-conditions land.
**Input**: User description: "Helm charts to deploy O3K on Kubernetes with two deployment modes: single-node and multi-node. Multi-node still runs the same single executable on every node, coordinating via the shared database."

## Clarifications

### Session 2026-06-02

- Q: In multi-node mode, how should VM lifecycle operations be guaranteed to reach the instance that hosts the VM (the product currently has no cross-node placement tracking)? → A: Fix the product in a separate workstream (post-condition WS-1: multi-node VM placement & request forwarding — track the hosting node per VM and synchronously forward lifecycle requests to the owning node; `SPEC-007-POSTCONDITIONS.md`). SPEC-008 stays a pure deployment spec; its multi-node mode (User Story 2) depends on that post-condition. The chart needs no client-affinity workarounds; single-node chart work proceeds independently of the VM-placement fix (it does, however, depend on SPEC-007's separately-scoped admin-password wiring — see round 3 — which is now delivered).
- Q: What should the chart's default container image source be? → A: No default — the image reference is a required install-time value; installation fails fast with a clear message when it is missing. No public image is pulled implicitly.
- Q: In multi-node mode, how are cluster nodes designated to run an O3K instance? → A: Label opt-in — only nodes carrying a configurable label (e.g. `o3k.io/compute=true`) run an instance. Designating a node = labeling the Kubernetes Node object (no chart upgrade or per-node config); un-designating = removing the label. Privileged/host access is confined to explicitly labeled nodes.
- Q: How should the Helm chart be distributed/consumed? → A: In-repo source only — the chart lives in the repo (e.g. `charts/o3k/`) and is installed from a local path/checkout; no registry publishing infrastructure is part of this feature. Publishing can be added later without rework.
- Q: What observability should the chart wire up by default? → A: Logs + health only — rely on the product's existing structured JSON logging (stdout, cluster-collected) plus liveness/readiness probes; no new metrics/tracing product code. Metrics/tracing deferred until the product exposes them.

### Session 2026-06-03

- Q: How should real-mode data (VMs, local volumes, local images) persist, given libvirt domains are tied to the node running them? → A: Node-local persistence — real-mode local data persists on the hosting node's storage and survives pod restarts on that node; it is not replicated across nodes (matches docker-compose-kvm). Networked backends (Ceph RBD, S3) remain configurable for volumes/images.
- Q: How should database schema migrations run, especially when N multi-node instances start concurrently? → A: ~~One-shot migration job — a pre-install/pre-upgrade hook runs migrations exactly once before any instance starts; instances do not migrate on startup.~~ **Superseded in round 4**: the product already migrates on startup with golang-migrate's lock serializing concurrent boots, so no dedicated job is needed — see round 4.
- Q: How should external clients reach services, and how should the service catalog advertise endpoint URLs? → A: Configurable endpoint host — the operator supplies one externally-reachable host/address; the chart exposes the services (mechanism selectable) and configures the catalog to advertise that address so clients receive reachable URLs. Internal-only (ClusterIP) by default.
- Q: Should single-node mode support real (privileged libvirt) operation? → A: Yes — node-count mode and service modes are independent; a single privileged node can run real VMs (mirrors docker-compose-kvm single-host production). Stub remains the default.

### Session 2026-06-03 (round 3)

- Q: Should the chart ship an in-cluster database, or only connect to an external one? → A: External database only — the chart never deploys a database; an operator-provided database is a hard prerequisite for all modes (single-node and multi-node). The bundled-DB option is dropped.
- Q: How should the chart handle the Redis cache (product default is cache disabled)? → A: External/optional, off by default — the chart deploys no Redis; caching is opt-in by setting the cache toggle and pointing `redis_url` at an operator-provided Redis. Matches the product default and production compose (KVM/Horizon run cache off; only the dev stack enables it). Constraints: in multi-node mode an enabled cache MUST be a single shared Redis (per-pod Redis breaks cross-node invalidation → stale reads); enabling the cache makes Redis a fail-fast startup dependency (boot-time Ping), so it must be reachable/health-gated before O3K.
- Q: How should the known default admin password (admin/secret, hardcoded in migration 002) be handled? → A: Enforce non-default at install — the chart requires an admin password (from a Secret) and fails fast if absent, like the JWT secret; no deployment runs with admin/secret. This needs a small product prerequisite, **folded into SPEC-007**: wire the already-present but currently-unused `keystone.admin_password` config field so the admin user is seeded/upserted with the provided password at bootstrap (the default is otherwise fixed in migration 002).
- Q: Should the chart provide TLS for the API endpoints (the binary serves plain HTTP)? → A: Optional TLS at the exposure layer — when external exposure is enabled, the chart supports TLS termination via Ingress (cert operator-supplied or cert-manager-issued; the chart does not generate certs or implement TLS). Cluster-internal/plain-HTTP remains the default. TLS implies the Ingress exposure path. (Corrected in round 4: advertising `https://` catalog URLs DOES require a small product change — see round 4.)

### Session 2026-06-03 (round 4 — deep design pass)

- Q: The catalog scheme is effectively hardcoded to `http://` (`keystone/auth.go` rewrites only the host); advertising `https://` for the optional-TLS decision needs a product change. How to handle? → A: Fold a configurable catalog scheme into SPEC-007 (alongside the admin-password wiring). The chart sets the scheme to `https` when TLS is enabled so clients receive correct `https://` endpoint URLs.
- Q: Migrations already run on every instance startup via golang-migrate (serialized by its DB lock, so no multi-node race); a dedicated one-shot Job that skips startup migration would itself need a product change. How to handle? → A: Rely on the existing startup migration plus golang-migrate's lock — no dedicated migration Job and no product change. Instances migrate on startup; the lock serializes concurrent boots and makes rolling upgrades safe (first new instance migrates, others no-op). This reverses the round-2 "one-shot job / instances do not migrate" decision.
- Q: The metadata service binds `localhost:8775` and nothing wires VM→169.254.169.254→:8775, so real-mode VMs can't fetch cloud-init metadata (SSH keys, user-data). How to handle? → A: Track the metadata routing fix as a post-condition (WS-4, `SPEC-007-POSTCONDITIONS.md`) — make the metadata service reachable from VMs (non-localhost bind + the 169.254.169.254 DNAT redirect / per-namespace routing) as a product change, so real-mode VMs receive cloud-init metadata and are loginnable. Required by real mode (single-node real and multi-node).
- Q: How should north-south connectivity work (VM→internet egress, and SSH from the internet→VM via floating IP), given the current model needs a pre-existing host external bridge? → A: Split egress and ingress, both tracked as post-condition WS-5 (`SPEC-007-POSTCONDITIONS.md`). **Egress**: automatic SNAT/masquerade out the node's existing primary uplink — no external bridge, no operator setup, works on cloud and bare metal. **Ingress**: keep real OpenStack floating IPs (100% API-compatible) drawn from an operator-supplied pool that routes to the nodes via MetalLB (cloud/bare metal) or a routed/L2 subnet (datacenter/lab); O3K programs the floating-IP DNAT on the node hosting the VM (reusing the WS-1 hosting-node tracking). The chart takes the floating-IP pool as config and documents the MetalLB recipe. The fully k8s-native "LoadBalancer Service per floating IP" model was rejected as too heavy (would couple O3K to the k8s API with async reconciliation).

### Session 2026-06-03 (round 5 — topology & operations)

- Confirmed (from code): O3K connects to a **host libvirtd** via the unix socket (`pkg/hypervisor/libvirt.go`, local dialer) and does not bundle qemu/libvirtd. Therefore real mode requires host libvirtd+qemu on each VM-hosting node (documented prerequisite, as in the KVM compose), the chart mounts the host libvirt socket, and VMs are host processes that **survive pod restarts/upgrades**.
- Q: What workload kinds should the chart use per mode? → A: Mode-specific. Single-node → Deployment (stub may scale to N stateless replicas for HA; real pins replicas=1 with Recreate strategy — brief unavoidable downtime on upgrade given privileged+hostNetwork+host ports). Multi-node → DaemonSet on labeled nodes (one identical instance per node).
- Q: How should the chart accept secrets (JWT, admin password, DB credentials)? → A: Both — chart creates a Secret from provided values for quick start, OR references an operator-pre-created Secret (`existingSecret`) for GitOps/production; required secrets fail fast if neither is supplied.
- Q: How should the chart handle Kubernetes admission for privileged (real-mode) pods? → A: Chart can apply the namespace PodSecurity `privileged` label (toggle, real mode only) and documents OpenShift SCC; stub mode runs unprivileged (passes restricted PSA). Targets vanilla k8s + k3s; OpenShift documented.
- Q: In multi-node, how do clients reach the API across N instances? → A: A single Service (ClusterIP; LoadBalancer/Ingress when external) load-balances across all instances, relying on the post-condition WS-1 any-instance-serves-any-request behavior; the configured endpoint host points at it. Metadata stays node-local (VMs reach it via link-local, not this Service).

### Session 2026-06-03 (round 6 — storage correctness)

- Q: Local Glance/Cinder storage is node-local (`/var/lib/o3k/images`, local volume path), so in multi-node real mode an image/volume on one node isn't available to VMs on another (boot/attach fails). How to handle? → A: Require a shared backend in multi-node real mode — Glance must use Ceph RBD or S3, and Cinder must use RBD; the chart rejects or hard-warns local backends in that mode and documents that local backends are single-node-only. Single-node real may still use local storage. Parallels the external-DB and shared-Redis decisions.

### Session 2026-06-03 (round 7 — DHCP & network durability)

- Confirmed (from code): O3K provides DHCP via `dnsmasq` (`pkg/networking/dhcp.go`), spawned per network inside the namespace. The reference image (`build/package/Dockerfile`) installs `iproute2/iptables/ipset` but **not `dnsmasq`** — so as built, real-mode DHCP fails and VMs get no IP. Decision: the O3K image used for real mode MUST include `dnsmasq` (plus `iptables`, `iproute2`, `ipset`); the reference Dockerfile must add `dnsmasq`.
- Q: dnsmasq runs as an O3K child process and O3K does not reconcile network state on startup, so after a pod restart/upgrade a real-mode VM survives (host libvirtd process) but loses its DHCP/networking. This contradicts FR-012c's "VMs survive upgrades." How to handle? → A: Track startup network reconciliation as post-condition WS-6 (`SPEC-007-POSTCONDITIONS.md`) — on startup O3K rebuilds DHCP servers, namespaces, bridges, and security-group rules from database state (as the VXLAN coordinator already re-syncs), so VM networking survives pod restarts/upgrades and genuinely matches VM-process survival.

### Session 2026-06-11 (round 8 — delivery scope)

- Q: Real-mode and multi-node depend on product post-conditions (WS-1/4/5/6, tracked in `SPEC-007-POSTCONDITIONS.md` / issue #52) that are not yet implemented. What is SPEC-008's definition of done? → A: Build the whole chart now (all modes, all templates), but **gate the real-mode and multi-node success criteria as deferred** until the post-conditions ship — specifically SC-003, SC-004, and the real-mode acceptance scenarios (cloud-init/login, floating-IP reachability, VM survival across restarts). The validated MVP that defines SPEC-008 "done" is **single-node stub mode (plus optional TLS)**; real-mode and multi-node templates are authored and `helm template`/lint-clean now, with their end-to-end validation gated on the post-conditions.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Single-Node Deployment with One Command (Priority: P1)

A platform operator or developer wants to run a complete, working O3K cloud (the OpenStack services — identity, compute, placement, network, block storage, image — plus the metadata service) on an existing Kubernetes cluster. They install the chart with a single command, optionally adjusting a small set of configuration values, and within minutes have OpenStack-compatible API endpoints they can use with the standard OpenStack CLI and Terraform provider — exactly as they would with the existing Docker Compose development stack.

**Why this priority**: This is the minimum viable deliverable. It replaces the manual Kubernetes manifests that operators currently have to copy from documentation, and it serves as the foundation the multi-node mode builds on. Without it, nothing else in this feature has value.

**Independent Test**: Can be fully tested by installing the chart on any Kubernetes cluster (including a local single-node cluster) with default values, then authenticating with the OpenStack CLI and completing a basic resource lifecycle (token issue, server create/list/delete in stub mode).

**Acceptance Scenarios**:

1. **Given** a Kubernetes cluster, a reachable external database, and no prior O3K installation, **When** the operator installs the chart providing the database connection, an image reference, and a secret (all other values defaulted), **Then** all seven service endpoints (identity, compute, placement, network, block storage, image, metadata) become available and report healthy within 5 minutes.
2. **Given** a running single-node installation, **When** a user authenticates with the OpenStack CLI using the seeded credentials, **Then** a token is issued and standard resource operations (list flavors, create/delete a server in stub mode) succeed without any client-side modification.
3. **Given** a running single-node installation, **When** the operator runs the chart's built-in verification test, **Then** the test confirms the identity endpoint answers correctly and reports success.
4. **Given** an operator who has not provided a signing secret for tokens, **When** they attempt to install the chart, **Then** the installation fails immediately with a clear message rather than starting with an insecure default.

---

### User Story 2 - Multi-Node Deployment Across Cluster Nodes (Priority: P2)

A platform operator wants to scale O3K across multiple Kubernetes worker nodes to run real virtual machines on more than one physical host. They switch the chart to multi-node mode; the chart then runs the same single O3K executable on every designated cluster node. Each instance automatically registers itself with a unique identity, all instances coordinate exclusively through the shared database, and virtual machines on different nodes can communicate with each other over the overlay network — with no per-node manual configuration.

**Why this priority**: Multi-node is the headline capability of this feature and the reason for choosing Kubernetes over Docker Compose, but it depends on the single-node foundation (chart structure, configuration, secrets, database wiring) being in place first.

**Independent Test**: Can be tested on a multi-node Kubernetes cluster by installing the chart in multi-node mode, verifying that every designated node runs exactly one instance, that all instances appear as registered and active compute nodes, and that two VMs placed on different nodes can reach each other over the network.

**Acceptance Scenarios**:

1. **Given** a Kubernetes cluster with N nodes carrying the configured designation label, **When** the operator installs the chart in multi-node mode, **Then** exactly one O3K instance runs on each labeled node and all N instances appear as active registered compute nodes within 60 seconds.
2. **Given** a running multi-node installation, **When** the operator applies the designation label to an additional node, **Then** an instance starts on it and self-registers without any chart upgrade or per-node configuration change.
3. **Given** a running multi-node installation, **When** the operator removes the designation label from a node, **Then** the instance on that node is evicted and the node is reported as inactive (running VMs on it are not migrated — see Edge Cases).
4. **Given** a running multi-node installation with VMs on two different nodes attached to the same tenant network, **When** one VM sends traffic to the other, **Then** the traffic is delivered across nodes via the overlay network.
5. **Given** a multi-node installation, **When** one node stops sending heartbeats (e.g., node failure), **Then** the remaining instances continue serving API requests and the failed node is reported as inactive.
6. **Given** a multi-node installation, **When** a user performs lifecycle operations (create, reboot, delete) on a VM, **Then** the operation reaches the instance that hosts that VM and completes successfully.

---

### User Story 3 - Configure, Upgrade, and Remove the Deployment (Priority: P3)

An operator managing a running O3K installation needs to change configuration (e.g., switch a service between stub and real mode, point at a different database, adjust resource limits), apply a new product version, and eventually remove the installation cleanly. All of this happens through standard chart operations against a single configuration values file — never by hand-editing deployed resources.

**Why this priority**: Day-2 operations make the chart production-credible, but they only matter once deployment itself (Stories 1 and 2) works.

**Independent Test**: Can be tested on an existing installation by changing a configuration value and upgrading (observing the change take effect), upgrading to a new image version (observing data survive), and uninstalling (observing no orphaned workloads remain).

**Acceptance Scenarios**:

1. **Given** a running installation, **When** the operator changes a configuration value and performs an upgrade, **Then** the new configuration takes effect without manual intervention and without data loss.
2. **Given** a running installation with existing resources (users, projects, instances), **When** the operator upgrades to a newer product version, **Then** all previously created resources remain intact and accessible afterward.
3. **Given** a running installation, **When** the operator uninstalls the release, **Then** all deployed workloads and services are removed, while persisted data is retained or removed according to an explicit operator choice.
4. **Given** an operator preparing an installation, **When** they review the chart's configuration reference, **Then** every supported value is documented with its purpose, default, and which mode(s) it applies to.

### Edge Cases

- What happens when the shared database is unreachable at startup? Instances must fail fast with a clear error (consistent with the project's fail-fast principle) and recover automatically once the database becomes available, rather than hanging or silently degrading.
- What happens when the token signing secret is not provided? Installation must refuse to proceed; it must never fall back to a known default secret.
- What happens when the admin password is not provided? Installation must refuse to proceed; no deployment may come up with the product's known default admin credentials.
- What happens when no external database is configured at install? Installation must fail fast with a clear message, since the chart deploys no database and a reachable external one is a hard prerequisite for every mode.
- What happens when caching is enabled in multi-node mode but pointed at per-instance (non-shared) Redis? The chart must reject or warn, since cross-node cache invalidation would not propagate and instances would serve stale reads; only a single shared Redis is valid.
- What happens when local Glance/Cinder backends are selected in multi-node real mode? The chart must reject or hard-warn, since images/volumes would be node-local and VMs on other nodes could not boot from them or attach them; a shared backend (RBD/S3) is required for multi-node real.
- What happens when TLS is enabled but no certificate (or cert-manager issuer) is available? Installation must surface the misconfiguration clearly rather than exposing an endpoint that advertises https but cannot terminate TLS.
- What happens when an instance restarts on the same node? It must re-register under the same node identity rather than accumulating duplicate registrations.
- What happens when two releases are installed in the same cluster? Installations must not collide — names, networks, and registrations must be scoped per release.
- What happens when a node is labeled for designation but lacks virtualization capability in multi-node real mode? The instance on that node must report a clear failure (via readiness/heartbeat) rather than appearing healthy while unable to run VMs; the operator is expected not to label incapable nodes.
- What happens when the designation label is removed from a node that is currently hosting VMs? The instance is evicted and those VMs are not migrated (the product has no live migration); they become unmanageable until the node is re-designated. This consequence must be documented so operators drain a node before un-designating it.
- What happens to in-flight API requests during an upgrade? Requests must not be routed to instances that are shutting down; clients see at most transient retryable errors.
- What happens to running VMs during an upgrade? They must survive — VMs are host libvirtd/qemu processes, not pod children — so a pod restart (single-node real Recreate, or multi-node DaemonSet rolling update) does not terminate them. Their networking must also survive: on startup O3K reconciles network state from the database (re-spawns DHCP, rebuilds namespaces/bridges/security groups) per FR-012g, so VMs do not lose connectivity. Single-node real mode incurs a brief API downtime during Recreate (one privileged/hostNetwork pod cannot overlap another on the same node); this is expected and documented.
- What happens when real mode is installed on a cluster enforcing default Pod Security admission? Privileged pods would be rejected; the chart must apply (or instruct the operator to apply) the namespace `privileged` PodSecurity level so admission succeeds, rather than failing opaquely.
- What happens when startup migration fails (e.g., database unreachable or a migration errors)? The instance must fail fast (not serve against an un-migrated or partially-migrated schema); the failure must be surfaced clearly and be safely retryable, and golang-migrate's lock must prevent concurrent instances from competing.
- What happens to a node's real-mode VM data when its instance pod is rescheduled onto the same node? The node-local data must still be present and the VMs recoverable; data must not be tied to the pod's ephemeral lifecycle.
- What happens when a VM lifecycle request arrives at an instance that does not host that VM? The product (per post-condition WS-1) forwards the request synchronously to the owning node and returns its response; if the owning node is inactive (missed heartbeats), the request fails fast with a clear error rather than hanging.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST provide an installable chart that deploys the complete O3K service set (identity, compute, network, block storage, image, metadata) to a Kubernetes cluster as a single release.
- **FR-002**: The chart MUST offer exactly two deployment modes — single-node and multi-node — selected by a single configuration value, with single-node as the default.
- **FR-003**: In single-node mode, the chart MUST run exactly one O3K instance serving all services.
- **FR-003a**: Deployment mode (single-node/multi-node) and service modes (stub/real per service) MUST be independent. Single-node mode MUST support real, privileged virtualization (libvirt) in addition to stub, so a single host can run real VMs. Stub MUST remain the default for all modes.
- **FR-003b**: The chart MUST use mode-appropriate workload kinds. Single-node MUST use a Deployment: in stub mode it MAY be scaled to multiple stateless replicas (all state in the database); in real mode it MUST pin a single replica with a Recreate update strategy (concurrent privileged/hostNetwork/host-port pods cannot coexist on one node). Multi-node MUST use a DaemonSet scheduled onto the designation-labeled nodes (exactly one instance per labeled node).
- **FR-004**: In multi-node mode, the chart MUST run one instance of the same, unmodified O3K executable on every designated cluster node; there MUST be no role differentiation (no separate controller/agent artifacts) between nodes.
- **FR-005**: In multi-node mode, each instance MUST automatically acquire a unique node identity and a node-reachable tunnel address, and MUST register itself without any per-node manual configuration.
- **FR-005a**: In multi-node mode, the set of nodes that run an instance MUST be determined by a node label opt-in: only nodes carrying a configurable designation label run an instance. Applying the label to a node MUST cause an instance to start and self-register, and removing the label MUST cause the instance to be evicted — both without a chart upgrade or per-node configuration change. Privileged/host-level access MUST be confined to labeled nodes.
- **FR-006**: All instances of a release MUST share a single, operator-provided external database; the chart MUST NOT deploy a database. A reachable external database is a hard prerequisite for all modes (single-node and multi-node).
- **FR-006a**: The chart MUST NOT deploy a Redis/cache component. Caching MUST be off by default (matching the product default) and opt-in via a configuration toggle plus an operator-provided `redis_url`. When caching is enabled in multi-node mode, the chart MUST require a single shared Redis (a per-instance cache is invalid because cross-node invalidation would not propagate, yielding stale reads). The chart MUST document that enabling caching introduces a fail-fast startup dependency on Redis reachability.
- **FR-007**: Sensitive values (token signing secret, database credentials, admin password) MUST be supplied through secure cluster-native secret storage. Installation MUST fail fast when the token signing secret is absent; no insecure default may be applied.
- **FR-007a**: The chart MUST require an administrator password (supplied via a Secret) and MUST fail fast when it is absent; no deployment may run with the product's known default admin credentials. This relies on a product prerequisite (folded into SPEC-007): the bootstrap MUST honor the supplied admin password (wiring the existing `keystone.admin_password` configuration field) so the seeded admin user is created/updated with it rather than the fixed default from the seed migration.
- **FR-007b**: The chart MUST accept secrets (token signing secret, admin password, database credentials, and any optional Redis/storage credentials) either by creating a Secret from supplied values OR by referencing an operator-pre-created Secret (`existingSecret`). When neither a value nor an existing Secret is provided for a required secret, installation MUST fail fast.
- **FR-008**: The chart MUST expose all O3K service endpoints on their canonical ports — identity 35357, compute 8774, **placement 8778**, network 9696, block storage 8776, image 9292, and metadata 8775 (seven HTTP servers in total) — and make them reachable per operator-configured exposure settings (cluster-internal by default, externally exposable by configuration). Placement MUST be treated like the other API services for exposure, catalog advertising, and health probing.
- **FR-008a**: The chart MUST accept a configurable externally-reachable endpoint host/address and configure the identity service catalog to advertise endpoint URLs at that address, so standard OpenStack clients (CLI, Terraform) receive URLs they can actually reach. The external exposure mechanism (e.g. LoadBalancer, NodePort, Ingress) MUST be selectable via configuration; exposure defaults to cluster-internal only.
- **FR-008b**: The chart MUST support optional TLS termination for externally-exposed endpoints via Ingress, referencing an operator-supplied or cert-manager-issued certificate (the chart MUST NOT generate certificates or implement TLS itself, as the product serves plain HTTP). When TLS is enabled, the service catalog MUST advertise matching `https://` URLs — this relies on a product prerequisite (folded into SPEC-007): the catalog endpoint scheme MUST be configurable (it is currently effectively fixed to `http://`). TLS MUST be off by default, with cluster-internal/plain-HTTP as the default posture.
- **FR-009**: In multi-node mode, the chart MUST enable cross-node tenant network traffic over the product's overlay network, including ensuring the required node-to-node transport (overlay tunneling port) is available between designated nodes.
- **FR-009d**: In multi-node mode, the chart MUST front the API with a single Service (cluster-internal by default; LoadBalancer/Ingress when externally exposed) that load-balances across all instances, relying on the product's any-instance-serves-any-request behavior (post-condition WS-1). The configured endpoint host (FR-008a) MUST resolve to this Service. The metadata service is excluded from this front door — it is reached by VMs node-locally via the link-local address (FR-009a).
- **FR-009a**: In real mode, VMs MUST be able to reach the metadata service at the standard link-local address (169.254.169.254). This relies on a product post-condition (WS-4, `SPEC-007-POSTCONDITIONS.md`): the metadata service must bind a VM-reachable address and the link-local redirect to it must be wired per the product's networking mode. The chart MUST deploy the metadata service consistent with this on every node that runs VMs.
- **FR-009b**: In real mode, VM egress to external networks (the internet) MUST work without an operator-provided external bridge or secondary NIC: outbound VM traffic is SNAT/masqueraded out the hosting node's existing primary uplink. This relies on a product post-condition (WS-5, `SPEC-007-POSTCONDITIONS.md`). No operator network setup is required for egress.
- **FR-009c**: In real mode, the chart MUST support inbound access to VMs from outside the cluster via standard OpenStack floating IPs (kept as real, API-compatible IP objects — no node-port substitution). Floating IPs are allocated from an operator-supplied pool that the operator routes to the nodes (e.g. via MetalLB, or a routed/L2 subnet); the chart MUST accept the pool as configuration and document the routing options. The product (post-condition WS-5, `SPEC-007-POSTCONDITIONS.md`) MUST program the floating-IP DNAT/return path on the node that hosts the target VM (reusing the WS-1 hosting-node tracking). The chart MUST NOT require O3K to integrate with the Kubernetes API for this.
- **FR-010**: Multi-node mode MUST rely on the product's node-aware VM lifecycle handling (post-condition WS-1: hosting-node tracking and synchronous request forwarding) so that any instance can correctly serve any VM lifecycle request; the chart MUST NOT depend on client-affinity workarounds. Multi-node mode MUST declare the minimum product version that includes the WS-1 post-condition.
- **FR-011**: The chart MUST expose the product's service mode configuration (stub/real per service, networking mode, storage mode) through configuration values, with safe defaults (stub) that work on any cluster without host privileges.
- **FR-012**: Real virtualization and real networking MUST be configurable, including the host-level access each instance needs (hypervisor socket, host network, host storage paths), and MUST be off by default.
- **FR-012c**: In real mode, the chart MUST connect O3K to a host-provided libvirt daemon by mounting the host libvirt socket; the chart MUST NOT run libvirtd/qemu inside the pod. A running host libvirtd + qemu/KVM on each VM-hosting node is a documented prerequisite. Because VMs are host processes, they MUST survive O3K pod restarts and upgrades — and their networking MUST also survive, per FR-012g.
- **FR-012f**: The O3K container image used for real mode MUST include the userspace tools the real datapath shells out to — `dnsmasq` (DHCP), `iptables`, `iproute2`, and `ipset` (plus the compiled eBPF object if eBPF mode is used). The project's reference image MUST be updated to include `dnsmasq`, which it currently lacks.
- **FR-012g**: Real-mode VM networking MUST survive O3K pod restarts and upgrades. This relies on a product post-condition (WS-6, `SPEC-007-POSTCONDITIONS.md`): on startup, O3K MUST reconcile network state from the database — re-spawning DHCP (`dnsmasq`) servers and rebuilding namespaces, bridges, and security-group rules — since these are otherwise lost when the pod that spawned them exits. Without this, a restart leaves surviving VMs without DHCP/connectivity.
- **FR-012d**: Real mode MUST run with the host-level privileges it requires (privileged container, host network, and the host libvirt socket and storage paths). For clusters enforcing Pod Security admission, the chart MUST be able to apply the `privileged` PodSecurity level to its namespace (a toggle used only in real mode) and MUST document the equivalent OpenShift SCC. Stub mode MUST run unprivileged and satisfy the `restricted` PodSecurity level.
- **FR-012a**: In real mode, node-local data (VM instances, locally-backed volumes, locally-backed images) MUST persist on the hosting node's storage and survive instance restarts on that node. This data is node-local and MUST NOT be assumed replicated or shared across nodes. Networked storage backends (e.g. Ceph RBD, S3) for volumes and images MUST remain configurable for operators who want shared storage.
- **FR-012e**: In multi-node real mode, the chart MUST require a shared storage backend — Glance images MUST use Ceph RBD or S3, and Cinder volumes MUST use RBD — because local backends store data node-locally and an image/volume on one node is not available to a VM on another (boot/attach would fail). The chart MUST reject or hard-warn local Glance/Cinder backends in multi-node real mode, and MUST document that local backends are single-node-only. Single-node real mode MAY use local backends.
- **FR-012b**: The chart MUST rely on the product's existing on-startup database migration (golang-migrate), whose database lock serializes concurrent instance starts and prevents competing or partial migrations. The chart MUST NOT add a separate migration job, and MUST ensure the database is reachable before instances start (startup migration fails fast if it is not). This holds for installs, multi-node concurrent boots, and rolling upgrades (the first updated instance migrates; others find the schema current and proceed).
- **FR-013**: Each instance MUST report liveness and readiness so the platform only routes traffic to instances that are actually able to serve requests, and replaces instances that become unhealthy.
- **FR-013a**: Default observability MUST consist of the product's existing structured JSON logs (emitted to standard output for cluster-level collection) plus the liveness/readiness signals of FR-013. The chart MUST NOT assume a metrics or tracing endpoint that the product does not already expose.
- **FR-014**: Chart upgrades MUST preserve all persisted state (database contents, stored images/volumes); uninstall MUST remove all deployed workloads. *(Deferred — the operator's explicit choice to **delete** persisted/runtime state on uninstall is tracked in issue [#53](https://github.com/cobaltcore-dev/o3k/issues/53): a blocking pre-delete cleanup hook that purges network namespaces/routes, libvirt domains, orphaned storage, and the PVCs Helm does not remove by default, so a redeploy starts from a pristine baseline. The default **retain** path and plain workload removal are in scope here; the `dataRetentionPolicy: delete` purge is implemented in #53.)*
- **FR-015**: The chart MUST include a built-in post-install verification that confirms the identity endpoint responds correctly, runnable on demand by the operator.
- **FR-016**: Multiple releases of the chart MUST be installable in the same cluster without naming, networking, or registration collisions.
- **FR-017**: Every supported configuration value MUST be documented with purpose, default, and applicable mode(s).
- **FR-018**: The container image reference MUST be a required install-time value with no default; installation MUST fail fast with a clear message when it is absent. The chart MUST never implicitly pull an unspecified public image.
- **FR-019**: The chart MUST be installable directly from its in-repository source (local path or checkout) without requiring a published chart registry. Setting up registry publishing is out of scope for this feature but MUST NOT be precluded by the chart's structure.

### Key Entities

- **Release**: One installed instance of the chart; owns all deployed resources, scoped so multiple releases can coexist.
- **Deployment Mode**: The single-node/multi-node selector; determines how many instances run and which coordination features are active.
- **O3K Instance**: One running copy of the single executable serving all seven HTTP services (identity, compute, placement, network, block storage, image, metadata); in multi-node mode there is exactly one per designated cluster node.
- **Node Identity**: The unique identity (ID, hostname, tunnel address) an instance registers under; survives instance restarts on the same node.
- **Shared State Store**: The single database all instances of a release connect to; the only coordination channel between instances (registrations, heartbeats, overlay allocations).
- **Configuration Values**: The operator-facing settings (mode, service modes, database connection, exposure, resources) driving the entire deployment; the sole interface for customization.
- **Secrets**: Sensitive values (token signing secret, admin password, database credentials) held in cluster-native secret storage, never in plain configuration.
- **Endpoint Host**: The externally-reachable address the identity service catalog advertises for all services; must resolve and route to the exposed endpoints from where clients run.
- **Node-Local Data**: Real-mode per-node data (VM instances, locally-backed volumes/images) bound to a specific node's storage; persists across instance restarts on that node, not replicated across nodes.
- **Startup Migration**: The product's on-boot schema migration (golang-migrate), serialized across concurrent instances by its database lock; brings the shared schema to the required version. No separate migration job is introduced by the chart.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An operator with a Kubernetes cluster and a reachable external database can go from nothing to a working single-node O3K cloud — authenticated via the standard OpenStack CLI — in under 10 minutes using a single install command supplying the database connection, an image reference, and a secret.
- **SC-002**: Existing OpenStack CLI and Terraform workflows run against a chart-deployed O3K without any client-side changes (100% of the workflows that pass against the Docker Compose deployment also pass against the chart deployment).
- **SC-003**: *(Deferred — validated once the real-mode/multi-node post-conditions ship; see issue #52 and the 2026-06-11 clarification.)* In multi-node mode on a cluster with N designated nodes, all N instances are registered and reported active within 60 seconds of installation completing.
- **SC-004**: *(Deferred — validated once the real-mode/multi-node post-conditions ship; see issue #52 and the 2026-06-11 clarification.)* Two VMs on different nodes attached to the same tenant network can exchange traffic in multi-node mode (verified by the existing multi-node networking test passing against a chart deployment).
- **SC-005**: A configuration change or product version upgrade completes with zero loss of previously created resources (verified by resource inventory comparison before/after).
- **SC-006**: After uninstall, zero orphaned workloads or service endpoints from the release remain in the cluster.
- **SC-007**: 100% of deployment customization is achievable through the documented configuration values file — no post-install manual edits to deployed resources are required for any supported scenario.

## Assumptions

- **Dashboard out of scope**: The Horizon dashboard, console proxy, and session cache (as found in the Docker Compose Horizon stack) are not part of this feature's initial scope; the chart covers the O3K core services only. Dashboard support can be specified separately.
- **Container image**: Per clarification, the chart ships with no default image reference — operators must supply one (published, private-registry, or locally built). Producing/publishing an official image is out of scope for this feature.
- **External database only**: Per clarification, the chart deploys no database; every mode requires an operator-managed external database reachable by all instances. No bundled/evaluation database is provided.
- **External cache only**: Per clarification, the chart deploys no Redis; caching is off by default and opt-in against an operator-provided Redis. In multi-node, an enabled cache must be a single shared Redis.
- **Shared storage for multi-node real**: Per clarification, multi-node real mode requires a shared image/volume backend (Glance: RBD or S3; Cinder: RBD); local backends are single-node-only because they store data node-locally. The chart does not deploy Ceph/S3; the backend is operator-provided and configured via values.
- **TLS terminates at the edge**: Per clarification, the product has no in-process TLS, so API encryption is provided (optionally) by Ingress termination using an operator-supplied or cert-manager-issued certificate. The chart does not generate certificates; enabling TLS assumes an Ingress controller (and, if used, cert-manager) is present in the cluster.
- **Cluster prerequisites for real mode**: Real virtualization assumes Linux worker nodes with virtualization support and a running hypervisor daemon; the chart configures access but does not install host prerequisites. VM egress to the internet requires no operator network setup (masquerade out the node uplink). Inbound floating-IP access requires the operator to route a floating-IP pool to the nodes — recommended via MetalLB (cloud/bare metal) or a routed/L2 subnet (datacenter/lab); the chart documents this but does not install MetalLB or configure host NICs/bridges.
- **Node-aware VM lifecycle handling is a product post-condition (WS-1)**: O3K currently places a VM on whichever instance serves the create request and does not track which node hosts it. Per clarification, this is fixed in the product via a separate workstream (post-condition WS-1: hosting-node tracking + synchronous request forwarding, `SPEC-007-POSTCONDITIONS.md`), which this feature's multi-node mode depends on. Even spread of VMs across nodes follows naturally from load-balanced request distribution; a dedicated scheduler remains out of scope.
- **One chart, two modes**: A single chart with a mode selector is assumed (rather than two separate charts), keeping configuration, documentation, and versioning unified.
- **Heartbeat/liveness semantics**: Node liveness in multi-node mode follows the product's existing heartbeat mechanism (an instance missing heartbeats for twice the heartbeat interval is considered inactive); the chart does not redefine these semantics.
- **In-repo chart distribution**: Per clarification, the chart is consumed from its in-repository source; no chart registry/publishing pipeline is built in this feature, though the chart structure must not preclude adding one later.
- **Observability scope**: Per clarification, default observability is the product's existing structured JSON logs plus health probes only. Metrics/tracing wiring is deferred until the product exposes the corresponding endpoints; it is not part of this feature.
- **Node-local real-mode data**: Per clarification, real-mode VM/local-volume/local-image data is node-local and survives pod restarts on the same node but is not replicated across nodes; there is no live migration of VMs between nodes. Operators wanting shared volume/image storage configure networked backends (Ceph RBD, S3).
- **Migrations run on startup**: Per clarification, schema migrations execute via the product's existing on-startup path; golang-migrate's database lock serializes concurrent instance boots, so no dedicated migration job is needed and rolling upgrades are safe.
- **Endpoint host reachability**: Per clarification, the operator-supplied endpoint host advertised in the service catalog is assumed to resolve and route to the exposed services from the clients' network; the chart configures advertisement and exposure but cannot guarantee external DNS/routing.

## Dependencies

- An operator-supplied O3K container image (required at install time per FR-018) compatible with the chart's expected configuration surface.
- The product's existing multi-node coordination capabilities (node registration, heartbeats, overlay network coordination via the shared database) — already present in the codebase.
- **SPEC-007** (`docs/specs/007-helm-prereqs-bootstrap-catalog/`) — the chart-shaping prerequisites, **implemented**; these gate chart **authoring**: (a) admin-password bootstrap wiring (FR-007a) — required by **all** modes; (b) configurable service-catalog scheme (FR-008b) — required only when optional TLS is enabled.
- **Post-conditions** (`SPEC-007-POSTCONDITIONS.md`) — internal product/runtime work that does **not** change the chart's manifests but that real-mode and multi-node deployments need in order to fully **function**; sequenced **after** the chart is authored: (WS-1) multi-node VM placement & request forwarding — required by multi-node mode (User Story 2); (WS-4) metadata service VM-reachability + 169.254.169.254 routing (FR-009a) — required by **real** mode; (WS-5) north-south networking (FR-009b/c) — egress masquerade out the node uplink, and floating-IP DNAT programmed on the hosting node — required by **real** mode; (WS-6) startup network-state reconciliation (FR-012g) — rebuild DHCP/namespaces/bridges/security-groups from the database on boot so VM networking survives restarts — required by **real** mode.
- Existing integration/verification suites (CLI lifecycle tests, multi-node networking test) used to validate chart deployments.
- A Kubernetes cluster (version per current upstream support policy) with sufficient privileges for the selected mode (stub mode requires none beyond standard workloads; real mode requires host-level access on designated nodes).
