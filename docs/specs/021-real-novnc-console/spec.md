# Feature Specification: Horizon compatibility — a real console / noVNC (F1)

**Feature Branch**: `feature/534` (feature id: `021-real-novnc-console`)
**Created**: 2026-07-30
**Status**: Draft
**Input**: cobaltcore-dev/cloud-storage#534 — "o3k — Horizon compat: wire a real console / noVNC (F1)" (sub-issue of #531, step **3 of 3 — do last**; parent epic #423). Grounded in the SPEC-018 verification report [`docs/compatibility/HORIZON_COMPATIBILITY_REPORT.md`](../../compatibility/HORIZON_COMPATIBILITY_REPORT.md) §F1 and its predetermination [`docs/specs/018-horizon-dashboard-verification/research.md`](../018-horizon-dashboard-verification/research.md) §U1.

## Context

The SPEC-018 Horizon verification (#482) produced nine findings. Eight are closed: F4/F5/F6/F9 in #532 (SPEC-019) and F2/F3/F7/F8 in #533 (SPEC-020), both already in this branch's base (`f306b2c`). **F1 is the last one open** — and the report's own summary now reads: *"What doesn't (as of 2026-07-29). **F1 only** — the noVNC console tab shows no guest."*

**What a user sees today.** In the real pass, opening an instance's **Console** tab in Horizon shows **"Unable to load Console"** and **"Console currently not available"**. No framebuffer, ever — in stub or real mode. The adjacent **serial Console Log** works and shows genuine guest boot output (`openstack console log show vm1` returns a real cirros boot plus a `vm1 login:` prompt); that is the interim workaround and must keep working.

**Why it fails** — four compounding gaps, all confirmed at code level:

1. **A fabricated address.** Console handlers return a hardcoded `http://localhost:6080/vnc_auto.html?token=…`. In a k3s deployment the browser resolves `localhost` to the *user's own machine*, so the request never leaves the laptop.
2. **A meaningless token.** The token is 16 random bytes, returned and immediately discarded — never persisted, never associated with an instance, never checked by anything. Two console requests yield two unrelated tokens; neither can be resolved back to a VM.
3. **A guessed console port.** The stored port is `5900 + (hash(instance-id) mod 1000)`, with an in-code comment conceding the hypervisor is never asked. Real VMs *do* get a graphical console (the domain definition requests an automatically assigned port), but nothing ever reads back the port the hypervisor actually chose.
4. **No proxy.** Lightstack runs no console proxy at all. The verification stacks ship a standalone console client pointed at a dead placeholder target purely to *reproduce* the failure. There is no component that could accept a token, resolve it, and relay a browser to a guest's framebuffer.

A fifth, adjacent gap: **the operator-facing configuration is fiction.** Four documents (`docs/SINGLE_NODE_DEPLOYMENT.md`, `docs/SCALING.md`, `docs/HORIZON_INTEGRATION.md`, `deployments/README-KVM.md`) instruct operators to set `nova.console_proxy_base_url`. No such setting exists in the product — the binary reads no console configuration whatsoever, so following the documentation changes nothing.

This feature makes the Console tab work: an instance's real framebuffer, reachable at an address the operator controls, behind a token that actually means something.

## Clarifications

### Session 2026-07-30

- Q: Console client + relay topology — who serves the noVNC client, and who relays the browser to the guest? → A: **Reuse the already-pinned `bonigarcia/novnc:1.3.0` image, unmodified, with its command overridden to run websockify directly** (`python3 -m websockify --web /root/noVNC --token-plugin <file-based plugin> --token-source <dir> 6080`). That one component serves **both** the noVNC static client and the token-resolving WebSocket relay. **Lightstack writes no relay code and takes no new dependency for it** — its only job is to maintain the token→target mapping the plugin reads. Verified empirically inside that exact image before deciding:
  - The image carries the full websockify source tree at `/root/noVNC/utils/websockify/`, including `token_plugins.py` with `ReadOnlyTokenFile`, `TokenFile`, `TokenFileName`, `BaseTokenAPI`, `JSONTokenApi`, `JWTTokenApi`, `TokenRedis`, `UnixDomainSocketDirectory`.
  - The command above starts and reports `Web server. Web root: /root/noVNC` + `proxying from :6080 to targets generated by TokenFile`.
  - **Only the file-based plugins work without modifying the image**: `requests` (needed by `JSONTokenApi`/`BaseTokenAPI`), the Python `redis` module (`TokenRedis`) and `jwcrypto` (`JWTTokenApi`) are all absent. `JWTTokenApi` is additionally unusable because a self-contained signed token cannot be revoked (FR-014).
  - `TokenFile.lookup()` re-reads its source on **every** lookup, so Lightstack writing an entry takes effect live and deleting one is revocation.
  - Rejected: vendoring noVNC's assets plus an in-process relay (a new WebSocket dependency and vendored third-party assets for no gain); adding `requests` to the image to use `JSONTokenApi` (forfeits the unmodified-upstream-image property held for the verification stack); kolla `nova-novncproxy` (needs a `nova.conf` and another image — the standing SPEC-018 §U1 rejection).
- Q: May the token→target mapping live in a directory under the node-local storage root? → A: **Yes — `/var/lib/lightstack/console-tokens/`, one file per token.** This reuses the existing node-local contract rather than inventing a path: `realMode.hostStoragePath` (`charts/lightstack/values.yaml`) is already `/var/lib/lightstack` and hostPath-mounted, the SPEC-011 initContainer already pre-creates the per-service subdirs (one more line), the teardown purge job already mounts that root, and `pkg/paths` already treats the layout as a contract. Consequences, all accepted: the proxy must be **co-located** with Lightstack (a node-local directory), must be able to **read** the entries (file mode vs. the proxy's UID is a real constraint), and expired-entry reaping becomes correctness rather than hygiene since the plugin re-reads the whole directory per lookup. The compose stack mounts no `/var/lib/lightstack` at all and needs none — it is stub-only, where FR-027's honest refusal applies.
- Q: How is the guest console protected from direct access, and what does a multi-node deployment do? → A: **The guest console binds loopback only; the proxy reaches it by sharing the node's network namespace. Multi-node console access is out of scope for this feature and for version 1.** Loopback binding makes the token the *sole* path to a guest, with no firewall rules to get wrong, and it costs nothing because the proxy already shares the host network namespace (FR-023c). Verified as workable: the chart mounts the **host's** libvirt socket and runs `hostNetwork` + `privileged`, so libvirtd and the qemu processes live in the host network namespace that a `hostNetwork` proxy pod shares. Single-node is the only supported and verified topology, matching SPEC-009; the former multi-node addressing requirement is **removed** rather than weakened (its identifier is retired and deliberately not reused, so no requirement in this spec bears that number), and the corresponding edge case is retired. The token record still carries the instance's host — the ticket asks for it and it costs nothing — but no cross-node resolution is attempted.
- Q: Which chart owns the console proxy, and does the Horizon chart stay verification-scoped? → A: **The proxy ships in the product chart (`charts/lightstack`); the Horizon chart is relocated to `charts/horizon` in this feature, with production hardening deferred.** Horizon plus memcached is production infrastructure, so the chart's current self-description ("verification infrastructure — NOT a product chart") is wrong and this feature stops asserting it. The proxy nonetheless stays with `charts/lightstack` because every requirement it has is a property of the Lightstack **node** — the token directory under `realMode.hostStoragePath` (FR-023b), the node network namespace needed to reach the loopback guest (FR-023c), and co-location with Lightstack; hanging it off the dashboard chart would pin Horizon to the hypervisor node permanently, when Horizon can otherwise run anywhere. The relocation is mechanical (move, chart metadata, build targets, documentation paths) and this feature must edit that chart regardless, to remove its now-superseded noVNC deployment. **Production hardening of the relocated chart is explicitly a follow-up**, so this feature stays reviewable as a console change.
- Q: Where is the console-token store of record — the token-file directory, or a database table? → A: **A new database table is the store of record; the token-file directory is a projection of it.** The plugin's file format is strictly `token: host:port`, so it cannot carry an expiry, an instance id, or a project — yet FR-013 (project-scoped issuance), FR-014 (invalidate on instance delete) and FR-016 (reap expired) all need exactly those. A table makes reverse lookups and reaping ordinary queries, matches the repo's existing migration + pgx idiom, and gives FR-015's compatibility view a natural source. The directory becomes a dumb, regenerable cache whose loss merely stops tokens from working — fail-closed. Rejected: encoding expiry and instance into filenames so the directory could stand alone (stringly-typed state, a directory scan per reverse lookup); reusing the existing per-instance console columns (one row per instance cannot hold several concurrent tokens).
- Q: When is the guest's console endpoint read back from the hypervisor? → A: **On every console request; never cached on the instance.** Correct by construction, and the call is already bounded by FR-007's ~1s fail-fast budget, so caching buys nothing worth the risk — the defect being fixed *is* a stale/invented port. Consequence: `instances.console_vnc_port` becomes dead outright rather than half-alive, and FR-004's "re-establish whenever it may have changed" is satisfied without needing to enumerate lifecycle transitions. Rejected: caching on the instance with refresh on stop/start/reboot/resume (correctness then depends on catching every transition); doing both (the cache earns nothing).
- Q: Do lifecycle transitions invalidate an instance's outstanding console tokens, or only deletion? → A: **Every transition that can move the endpoint invalidates them — stop, start, reboot, resume, as well as delete.** This closes a genuine cross-instance leak rather than narrowing it: the mapping entry freezes `host:port`, and the hypervisor hands out console ports sequentially, so an instance that stops and frees port *P* can have *P* reassigned to a different instance while a still-valid token points at it — surfacing another tenant's framebuffer. A short lifetime is a probability argument; invalidation is a correctness one, and it costs one delete-by-instance at handlers this feature already edits. Users re-open the Console tab after a reboot regardless. Rejected: relying on the lifetime alone; re-verifying the endpoint at connect time (the proxy resolves tokens itself and cannot call back without the rejected HTTP-callback plugin).
- Q: How does stub mode express "no console"? → A: **Refuse at request time**, with an error naming stub mode as the reason. Immediate and diagnosable rather than an opaque failure discovered in a browser, consistent with FR-006's handling of a not-running instance, and truthful — a stub deployment has no guest to show. Consequence: stub mode stops returning 200 plus a URL, so the two console test scripts must be rewritten (already planned, since they currently assert only that *a* URL came back and therefore pass against the broken implementation). In the dashboard the Console tab reads "unavailable" in stub mode, which is the fact. Rejected: issuing a well-formed link that fails on connect (reproduces the F1 experience — no proxy need even be deployed in stub); serving a synthetic canned framebuffer (a fake, and well outside this feature).
- Q: May an admin open a console for another project's instance? → A: **Yes — owner's project by default, and a token carrying the `admin` role may open a console for any project's instance.** This matches upstream Nova, whose `os-remote-consoles` policy is `rule:admin_or_owner`, and reuses the authz pattern #533/SPEC-020 already established for the quota endpoints (scope reads to the caller's project; an `admin` token may query any project). Diverging would leave the Admin → Instances panel's Console tab silently broken for instances the admin does not own. The existing shared role-check helper (`common.HasRole`, adopted repo-wide in #533) is the mechanism. Rejected: strict owner-only (breaks the Admin panel and diverges from upstream); admin-only (guts the feature).
- Q: What shape does the operator-facing console address setting take? → A: **Keep the already-documented key name, but its value is the origin only (`scheme://host:port`); Lightstack appends the client page and the token query itself.** The page name and the token encoding are coupled to the client/proxy version — our choice, not the operator's — so owning that suffix in code makes a whole class of misconfiguration impossible. Grounded in a correction found while deciding: the pinned image's tag (`1.3.0`) is the **image's** version and it actually ships **noVNC 1.6.0**, serving `index.html`, `vnc.html` and `vnc_lite.html` — there is **no `vnc_auto.html`**. So the four deployment guides are wrong twice over (an unimplemented key *and* a page that does not exist), and their example values lose the `/vnc_auto.html` suffix. Rejected: having the key hold the full page URL (hands every operator a version-coupled detail); replacing it with discrete host/port/scheme keys (more knobs, and all four documents get rewritten rather than corrected).
- Q: When two viewers open the same instance's console, do they share the screen or does the newest win? → A: **Shared — several viewers of one instance see the same guest concurrently and nobody is dropped.** The console is a support tool and two people looking at one broken guest is the common case; a silent disconnect looks like a defect. There is no security cost, since every viewer had to hold a valid token for that same instance. This requires explicitly asking the hypervisor for a shared console rather than inheriting its default, which drops earlier viewers when a client requests exclusive access. FR-018's original wording ("isolated" for same-instance sessions) was incoherent and is corrected. Rejected: the hypervisor default (newest silently kicks the previous viewer); leaving it unspecified (behaviour would depend on what each client happens to request — untestable, which is how the current console reached its state).
- Q: What happens to the dead per-instance console port and password columns? → A: **Stop writing both and drop both columns in this feature's migration** (the down-migration restores them). The password has been generated and stored on every console request since its migration and **never applied to a domain**, and reading the endpoint per request (FR-004) has just made the stored port dead too. With the guest bound to loopback and the proxy the only route in, the token *is* the security boundary. Rejected: leaving the columns in place unused (two dead columns to confuse the next reader); implementing VNC password authentication (actively worse — the relay performs no VNC authentication, so the password would have to be handed to the browser in a URL, leaking it to the user and into logs; upstream avoids VNC passwords for the same reason).

### Revised in review (PR #80, 2026-09-24)

- **The guest console is a per-start UNIX socket, not a loopback TCP port** — superseding the loopback answer above (Q on direct access). A token froze a `host:port`, and libvirt hands a freed port to the next guest that starts, so any path that freed a console without Lightstack seeing it — a guest powering itself off, a crash, the window of a graceful shutdown, a console issued mid-transition — left a live link to whichever guest came next. With `<listen type='socket'/>` libvirt creates the socket in the domain's private directory (`domain-<id>-<name>`), so the path changes on every start and a stale token names nothing. Verified against libvirt 10.0 and the pinned websockify, whose `TokenFile` resolves `token: unix_socket:<path>` and relays through a read-only mount. The proxy no longer needs the node network namespace to reach a guest; it needs libvirt's domain directory and `DAC_OVERRIDE` instead (FR-017, FR-023c).
- **Tokens are also checked against libvirt, not only revoked on API calls** (new FR-014a). The reconciler compares every live token with the socket its guest serves now and revokes those whose guest serves another or none — the server-side form of upstream Nova's per-connection `validate_console_port`, which websockify cannot do.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - See and use a running instance's console from the dashboard (Priority: P1)

A project user opens Horizon, selects a running instance, and clicks the **Console** tab. The guest's screen appears — the same picture the hypervisor is drawing — and the user can type into it: hit Enter, get a login prompt, log in, run a command. This is the ordinary "my instance won't boot / lost its network / I need to fix SSH" workflow, and it is the only way in when SSH is unavailable.

**Why this priority**: This is the ticket's entire acceptance criterion and the last open finding from the #482 verification. Everything else in this feature exists to make it safe, configurable, and honest.

**Independent Test**: Boot an instance in real mode, open its Console tab in Horizon, and confirm the guest's live output is rendered and responds to keystrokes. Verifiable on its own, against a single instance, with no other story implemented.

**Acceptance Scenarios**:

1. **Given** a running instance in real mode, **When** its Console tab is opened in the dashboard, **Then** the guest's live framebuffer is displayed (for the cirros test image, its boot output and login prompt).
2. **Given** the console is displayed, **When** the user types into it, **Then** the keystrokes reach the guest and the guest's response appears — a user can log in and run a command without leaving the browser.
3. **Given** a running instance, **When** a console URL is requested from the command line (`openstack console url show`), **Then** the returned URL opens the same working console when pasted into a browser.
4. **Given** an instance that has been rebooted (so the hypervisor may have assigned it a different console endpoint), **When** its Console tab is opened again, **Then** the console still displays that instance's framebuffer — never another instance's, and never a dead connection.

---

### User Story 2 - Console access is scoped, time-bounded, and unforgeable (Priority: P2)

A console URL is a direct line into a virtual machine — it bypasses SSH keys, guest firewalls, and every in-guest control. So the link the user is handed must open exactly one instance, only for the person entitled to it, and only for a short while. Anyone who obtains a stale or invented link gets nothing.

**Why this priority**: A working proxy without this is strictly worse than the broken console it replaces — it would relay any caller to any guest. It ships with US1, not after it.

**Independent Test**: Request a console for instance A, then attempt to reach instance B's console with A's link, attempt to reuse a link past its lifetime, and attempt an invented link. All three are refused, while the legitimate link works.

**Acceptance Scenarios**:

1. **Given** a console link issued for instance A, **When** it is used to request a console session, **Then** it connects to instance A and to no other instance.
2. **Given** a console link that has passed its validity window, **When** it is used, **Then** the connection is refused with a clear reason and no guest is contacted.
3. **Given** an invented, altered, or already-invalidated link, **When** it is used, **Then** the connection is refused — the system never falls back to connecting "anyway".
4. **Given** a user authenticated for project X, **When** they request a console for an instance in project Y, **Then** the request is refused, exactly as instance reads already are.
5. **Given** an instance is deleted, stopped, started, rebooted or resumed, **When** a link issued before that operation is used, **Then** the connection is refused — it can never reach a console port since reassigned to another instance.
6. **Given** the console service is restarted, **When** a link issued before the restart is used within its validity window, **Then** it still works (links are not lost with process state).

---

### User Story 3 - The operator decides where the console lives (Priority: P3)

An operator deploying Lightstack — on a workstation with the compose stack, or on a cluster with the Helm chart — sets the address at which users' browsers reach the console, and that is the address users get. Nothing in the product assumes the browser runs on the same machine as the hypervisor.

**Why this priority**: Without it, US1 is only reproducible in one topology. It also closes the documentation gap: four operator documents describe a console setting the binary ignores today.

**Independent Test**: Set the console address to the deployment's externally reachable host, request a console URL, and confirm the returned URL carries that host — then confirm the URL works from a browser on a different machine.

**Acceptance Scenarios**:

1. **Given** an operator has configured a console address, **When** any console URL is issued, **Then** it uses that address — host, port, and scheme — verbatim.
2. **Given** no console address has been configured, **When** a console URL is issued, **Then** it is derived from the same endpoint settings the rest of Lightstack's catalog uses, and never contains a hardcoded `localhost` the operator did not ask for.
3. **Given** the documented deployment recipes are followed exactly, **When** the operator sets the documented console setting, **Then** it takes effect (the documentation and the product agree).
4. **Given** the standard deployment artifacts (compose stack and Helm charts), **When** they are brought up, **Then** the console endpoint is reachable from a browser without hand-editing manifests.

---

### User Story 4 - Honest answers for the consoles Lightstack does not serve (Priority: P4)

A user or tool that asks for a console type Lightstack cannot deliver is told so, immediately and in the standard shape, instead of receiving a plausible-looking URL that leads nowhere. Whoever asks for the serial log still gets the serial log.

**Why this priority**: The current fabricated URLs cost real debugging time — the SPEC-018 pass spent effort establishing that a 200 OK with a URL meant nothing. Cheap to fix, and it prevents the same wasted hour later.

**Independent Test**: Request each unsupported console type and confirm a clear refusal rather than a URL; request the serial console log and confirm it still returns guest output.

**Acceptance Scenarios**:

1. **Given** a request for a console type Lightstack does not serve, **When** it is made, **Then** the response is a clear, standards-shaped refusal naming the unsupported type — not a URL.
2. **Given** a running instance in real mode, **When** its serial console log is requested, **Then** it returns the guest's captured boot output exactly as it does today.
3. **Given** stub mode (no hypervisor, no guest), **When** a console is requested, **Then** the request is refused outright with stub mode named as the reason — no link is returned.

---

### Edge Cases

- **Instance not running** (stopped, paused, or still building): a console request must say so rather than hand out a link to a nonexistent framebuffer.
- **Console endpoint moved**: the hypervisor creates the console socket per start, so it differs after every stop/start. Since the endpoint is read fresh per request (FR-004), the residual case is a token issued *before* a restart and used after it — it must connect to nothing, never to another guest (FR-014a, FR-017).
- **Instance has no console device**: an instance whose definition carries no graphical console gets a clear refusal.
- **Hypervisor unreachable**: a console request must fail fast (the project's ~1 second budget), not hang the browser.
- **Guest reachable directly**: the guest's console endpoint must not be a way around the token — someone who can reach the host must still not be able to open a guest's framebuffer without one.
- **Instance deleted mid-session**: an open console session must terminate cleanly, not linger against a dead or reassigned endpoint.
- **Several sessions at once**: two users on two instances must never see each other's screens; two viewers on *one* instance must both keep working, neither evicting the other.
- **Link hoarding**: repeatedly requesting console links must not accumulate unbounded state; expired links must be reaped.
- **Mixed scheme**: a dashboard served over HTTPS embedding a plain-HTTP console is blocked by browsers — the console scheme must be configurable to match.
- **Proxy separated from the mapping**: the token→target mapping is node-local, so a proxy scheduled away from the Lightstack instance that wrote it sees an empty directory and refuses every token. Placement must be pinned, not left to chance.
- **Idle or abandoned session**: a browser that closes or stalls must not leave a session holding the guest's console open forever.

## Requirements *(mandatory)*

### Functional Requirements

**Showing the guest (US1)**

- **FR-001**: For a running instance in real mode, the system MUST return a console URL that, opened in a browser, displays that instance's live framebuffer.
- **FR-002**: The console session MUST be interactive — keyboard and pointer input from the browser MUST reach the guest.
- **FR-003**: The console endpoint used MUST be the one the hypervisor actually assigned to that instance, obtained from the hypervisor — never computed, guessed, or derived from the instance identifier.
- **FR-004**: The system MUST NOT serve a stale console endpoint. The endpoint MUST be read from the hypervisor **on every console request** and MUST NOT be cached on the instance record, so no lifecycle transition can leave a stale value behind.
- **FR-005**: Both console request paths that Horizon and the OpenStack CLI use — the current remote-console request and the legacy VNC-console action — MUST return equivalent, working URLs for the same instance.
- **FR-006**: Requesting a console for an instance that is not running, or that has no graphical console, MUST return a clear refusal naming the reason, not a URL.
- **FR-007**: The hypervisor readback inside a console request MUST be bounded by an explicit **1 second** deadline and fail rather than wait when the hypervisor is unreachable or slow. The end-to-end request stays under the 2 seconds SC-010 measures; the 1 second governs the external call, per the project's fail-fast rule.

**Making it safe (US2)**

- **FR-008**: Every console URL MUST carry a token that the system can resolve back to exactly one instance, together with the host and endpoint needed to reach it.
- **FR-009**: Console tokens MUST be persisted in the service's database as the single store of record, carrying at least the instance, project, host, endpoint, issue time and expiry, so a token issued before a service restart remains usable for the remainder of its validity window.
- **FR-010**: Console tokens MUST expire after a bounded, operator-configurable lifetime (default: 10 minutes), after which they MUST be refused.
- **FR-010a**: A token remains usable for repeated connections throughout its validity window, so the bounded lifetime is the **only** limit on reuse. Single-use semantics are deliberately not required: the proxy resolves tokens from the mapping directory independently (FR-023a/FR-023b), so a connection is never observable to Lightstack and could not be counted. Page refreshes and client reconnects therefore work, and the short default lifetime is what bounds exposure.
- **FR-011**: The console proxy MUST refuse any connection whose token is absent, unknown, expired, or no longer resolves to an existing instance — with no fallback path that connects without a valid token.
- **FR-012**: A token MUST grant access only to the instance it was issued for; it MUST NOT be usable to reach any other instance, and the target instance MUST NOT be selectable by the caller at connect time.
- **FR-013**: Console tokens MUST only be issued to a caller authorized for the instance's project, matching the project scoping already applied to instance reads. A caller holding the `admin` role MUST be able to open a console for an instance in **any** project, so the administrative instance panel works; every other caller is confined to their own project.
- **FR-014**: Any operation that can move or free an instance's console endpoint MUST invalidate that instance's outstanding console tokens — stop, start, reboot, suspend, resume, shelve, delete and force-delete. A token MUST NEVER be able to resolve to a console endpoint that has since been given to a different instance.
- **FR-014a**: Tokens whose guest no longer serves the console they name — it stopped, crashed, or restarted, with or without an API call — MUST be revoked within one reconcile interval. A readback that cannot answer (the hypervisor unreachable) MUST NOT revoke; the check repeats on the next sweep.
- **FR-015**: The system MUST expose a token-validation view compatible with the OpenStack console-auth-token API, returning the console connection details for a valid token and a not-found result for an invalid or expired one. This view exists for **API compatibility**; it is not the path the relay uses to resolve tokens (see FR-023b), and the console MUST NOT depend on it working.
- **FR-016**: Expired and invalidated token records MUST be reclaimed automatically, so token state cannot grow without bound.
- **FR-017**: An instance's console MUST NOT listen on TCP at all. It MUST be a **UNIX socket that the hypervisor creates per start** in the domain's private directory, so the token-validating proxy is the sole path to a guest's framebuffer, no firewall rule is load-bearing, and no console endpoint outlives its guest to be handed to another. A domain whose console is a TCP listener MUST be refused, not proxied. Because the proxy runs as its own component (FR-023a), it MUST be placed so that it can still reach that socket (FR-023c).
- **FR-018**: Concurrent console sessions to **different** instances MUST be isolated — no session may ever show another instance's framebuffer or receive its input.
- **FR-018a**: Concurrent console sessions to the **same** instance MUST be shared: every viewer sees that guest simultaneously and opening a new session MUST NOT disconnect an existing one. The system MUST request a shared console from the hypervisor explicitly rather than inheriting a default that evicts earlier viewers.
- **FR-019**: A closed, dropped, or idle browser session MUST release its hold on the guest console. Closed and dropped sockets are released by the relay inherently; **idle sessions require an explicit idle timeout to be configured**, since the relay disables it by default — an abandoned tab must not hold a guest console open indefinitely.

**Placing it (US3)**

- **FR-020**: The address at which browsers reach the console MUST be operator-configurable as a single **origin** (scheme, host, port) under the key the deployment guides already name, and that origin MUST appear verbatim in every issued console URL. The client page path and the token query MUST be appended by the system, not configured, so they cannot drift from the deployed client and proxy.
- **FR-021**: With no console address configured, the system MUST derive one from the same endpoint configuration that governs Lightstack's other advertised endpoints, and MUST NOT emit a hardcoded `localhost` the operator did not configure.
- **FR-022**: The operator documentation MUST describe only settings the product actually honors, with values that actually work: the currently documented-but-ignored console setting MUST become real (FR-020), and its example values MUST name a client page the deployed client genuinely serves.
**FR-023 series — how the console is deployed.** (This heading replaces a former umbrella requirement that merely restated the sub-requirements below; the testable content lives in FR-023a–e.)

- **FR-023a**: The console client and the relay MUST both be provided by the already-pinned upstream noVNC image, **unmodified**, with its start command overridden to run websockify serving the bundled client and resolving each connection's token through a file-based token plugin. Lightstack MUST NOT implement a WebSocket relay itself and MUST NOT take a new dependency for one.
- **FR-023b**: Lightstack MUST maintain the token→target mapping the plugin reads as one entry per token in a node-local directory under the existing storage root (`/var/lib/lightstack/console-tokens/`), created by the same mechanism that pre-creates the other node-local subdirectories. This directory is a **projection of the persisted store (FR-009), never the store of record**: writing an entry makes a token usable, removing it revokes that token (the mechanism behind FR-014 and FR-016), and losing the directory MUST fail closed — tokens stop working rather than becoming unvalidated.
- **FR-023c**: The proxy MUST be co-located with the Lightstack instance whose directory it reads (the mapping is node-local) and MUST see the hypervisor's per-domain directories at the paths the hypervisor reports, with the privilege to connect to a socket the hypervisor's user owns. Its file access MUST be arranged so it can read the entries under whatever user it runs as.
- **FR-023d**: The console proxy MUST be shipped by the **product** chart, pinned to the same node as the Lightstack instance it serves. It MUST NOT be a component of the dashboard chart, which must remain deployable independently of the hypervisor node.
- **FR-023e**: The dashboard chart MUST be relocated out of its verification-only location into the product chart directory, with its metadata, build/lint targets, and documentation references updated to the new path, and its superseded noVNC deployment removed. Its self-description MUST stop claiming it is not a product chart.

**Being honest (US4)**

- **FR-025**: Console types the system cannot serve MUST return a clear, standards-shaped refusal naming the unsupported type, instead of a URL that cannot work.
- **FR-026**: The serial console log MUST continue to return the guest's captured output unchanged — it remains the documented fallback.
- **FR-027**: In stub mode, a console request MUST be refused **at request time** with an error naming stub mode as the reason. It MUST NOT return a link, well-formed or otherwise.
- **FR-027a**: Where no console proxy is deployed — multi-node, which v1 does not support, or the proxy disabled — a console request MUST be refused with upstream's answer for a disabled VNC console (`400`, "Unavailable console type novnc"), never answered with a link. The chart MUST NOT deploy a proxy that can serve only one node of several.
- **FR-028**: Console issuance and connection outcomes (issued, validated, refused-and-why, closed) MUST be observable in the service logs, without recording token values in a form that would let a reader reuse them.

**Not regressing**

- **FR-029**: Behavior of all other compute API operations MUST be unchanged; this work MUST NOT alter instance create, read, update, delete, or action semantics beyond the console endpoints named here.
- **FR-030**: The verification report MUST be updated to record F1's resolution and the evidence for it, consistent with how F2–F9 were recorded.

### Key Entities

- **Console token**: A single-instance, time-limited credential handed to a browser. Carries which instance it opens, which project it belongs to, which host and endpoint reach the guest, when it was issued, and when it stops working. Persisted in the database as the store of record; mirrored into the node-local mapping directory the proxy reads; reclaimed from both once expired or invalidated.
- **Instance console endpoint**: Where a running instance's framebuffer actually lives, as reported by the hypervisor — host plus port. A property of the running instance, not of its record; it may change each time the instance starts.
- **Console session**: One live relay between a browser and a guest's console, established only after a token is validated, isolated from other sessions, and torn down when either side goes away.
- **Console address configuration**: The operator-set, browser-reachable base address (host, port, scheme) that the product puts into every console URL it issues.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In the real-mode pass, the dashboard's Console tab for a running instance renders the guest's live framebuffer within 10 seconds of opening the tab — captured as a screenshot showing the cirros login prompt.
- **SC-002**: A user logs into the guest and runs a command entirely through the dashboard console, with no SSH and no host shell.
- **SC-003**: 100% of issued console URLs carry the operator-configured address; zero contain a host the operator did not configure.

- **SC-005**: 0 of 5 unauthorized-access attempts succeed — another instance's link, an expired link, an invented link, a cross-project request, and a link reused after its instance was stopped — by the API or by the guest itself — and started again.
- **SC-006**: After stopping and restarting an instance, a freshly requested console connects to that instance on the first attempt (no stale-endpoint failure).
- **SC-007**: A console link issued before a service restart still works after it, within its validity window.
- **SC-008**: Two concurrent console sessions to two different instances each show their own guest, with no cross-talk, for at least 2 minutes; and two concurrent sessions to the *same* instance both stay connected and show that guest, neither evicting the other.
- **SC-009**: The serial console log still returns real guest boot output — the documented fallback is unregressed.
- **SC-010**: A console request with the hypervisor unreachable returns an error in under 2 seconds rather than hanging.
- **SC-011**: Every console setting named in the operator documentation demonstrably changes behavior when set (currently 0 of 1 does).
- **SC-012**: F1 is recorded as fixed in the verification report, leaving **0** open findings from the #482 verification pass.

## Scope

### In scope

- The graphical (VNC/noVNC) console for instances in real mode: endpoint readback, token issuance and validation, the proxy that relays a browser to a guest, and the token-validation view.
- Operator-configurable console addressing, wired through the compose stack and the Helm charts, with the operator documentation reconciled to it.
- Relocating the dashboard chart from its verification-only location into the product chart directory (mechanical move: chart metadata, build targets, documentation paths) and removing its superseded noVNC deployment.
- Honest refusals for unsupported console types and for stub mode.
- Verification in both stub mode (honest refusal) and real mode (working framebuffer), reusing the SPEC-018 runbooks and charts.

### Out of scope

- **SPICE, RDP, and interactive serial-over-websocket consoles** — refused honestly (FR-025), not implemented. The serial console *log* stays as-is.
- **Patching Horizon.** Fixes are Lightstack-side against stock, unmodified Horizon, as established for #532/#533.
- **Multi-node console access — entirely, for this feature and for version 1.** Single-node real mode is the only supported and verified topology (SPEC-018/SPEC-009). The token record still carries the instance's host, but no cross-node addressing, routing, or per-node proxy is built or specified.
- **Console session recording, auditing beyond service logs, or per-session rate limiting.**
- **Production hardening of the relocated dashboard chart** — a values schema, an ingress/TLS story, secret handling for the dashboard's signing key and memcached, and the settings-file duplication its sync target papers over. The relocation happens here; making that chart production-grade is a follow-up ticket.
- **The other open findings** (F10–F13, F15, F16) — separate tickets.

## Assumptions

- **Acceptance is measured in the SPEC-018 real pass**, reusing its existing harness: Lightstack on k3s in real mode via `charts/lightstack`, Horizon via the relocated dashboard chart (unmodified upstream image), Ceph/RGW via Rook, per `docs/specs/018-horizon-dashboard-verification/HOST_TESTING_REAL_MODE.md`. Stub mode is verified for honest behavior only (FR-027) — a stub deployment has no guest to display. The SPEC-018 runbooks reference the chart's old path; this feature's own runbook uses the new one, and the SPEC-018 spec directory is not edited (it belongs to another feature).
- **The interim workaround stays supported.** `openstack console log show` remains the documented fallback and is treated as a regression if it breaks.
- **Default token lifetime is 10 minutes**, matching the upstream OpenStack default, and is operator-configurable.
- **The guest's console is a per-start unix socket** so the proxy is the only route to it and no stale token can reach another guest (FR-017). Before this feature the domain definition listened on all interfaces, which made any token bypassable from anywhere that could reach the node.
- **The existing stored console fields are removed, not repaired.** The instance record's console port and password are both dead — the port is fabricated and now read per request instead (FR-004), and the password was never applied to a guest at all — so this feature drops both columns rather than leaving them to mislead.
- **`console_proxy_base_url` is the name to keep** for the operator-facing console address, since four deployment documents already instruct operators to set it — unless planning finds a reason to rename, in which case those documents change with it.
- **Token issuance stays synchronous**, in line with the project's no-queues rule: a console request resolves the endpoint and returns a usable URL before responding.
- **One instance, one framebuffer.** Instances are assumed to expose a single graphical console; multi-head guests are not modeled.

### Deferred design decisions

All four forks recorded at spec time were resolved in the 2026-07-30 clarification session:

1. ~~Where the browser-side console client comes from~~ — the pinned upstream noVNC image serves it (FR-023a).
2. ~~Whether the relay runs inside the Lightstack process~~ — it does not; websockify in that same image is the relay (FR-023a).
3. ~~Where token records live~~ — a database table is the store of record, the node-local directory a projection (FR-009, FR-023b).
4. ~~How stub mode expresses "no console"~~ — refused at request time, naming stub mode (FR-027).
